## 1. Incident timeline 2025–2026: what happened, root cause, what would have prevented it

### Takeaway
Between March 2025 and October 2026 the dominant pattern was a chain reaction: one stolen CI credential (usually leaked through a `pull_request_target` "pwn request" or a mutable tag) was used to poison a widely trusted tool, which then harvested the next victim's CI credentials. From March 2026 the poisoned tools were security scanners themselves (Trivy, Checkmarx KICS/AST) and the campaign cascaded into AI tooling (LiteLLM) and a password-manager CLI (Bitwarden). Controls that verifiably held: full-SHA pins to known-good commits, digest-pinned images, lockfiles, and release-age cooldowns.

### Inferences
- **Common patterns (each seen in ≥2 incidents above):**
  1. Mutable tags repointed (tj-actions, reviewdog, trivy-action, setup-trivy, KICS).
  2. `pull_request_target` + untrusted input/checkout (Nx, hackerbot-claw→Trivy, reportedly SpotBugs→tj-actions).
  3. Long-lived tokens (tj-actions-bot PAT, Nx npm token, Cline npm token, Trivy PAT, LiteLLM engineers' `gh` OAuth tokens).
  4. Install-time scripts (`postinstall`/`preinstall`, Python `.pth`).
  5. Credential harvesting from `Runner.Worker` memory (tj-actions, Trivy) — this defeats log masking and reads every secret the job has, not just those passed to the step.
  6. Exfiltration via the victim's own GitHub account (s1ngularity, Shai-Hulud, `tpcp-docs-`), which evades domain allowlists that permit `github.com`.
  7. Self-propagation with stolen publish tokens.
  8. Incomplete remediation enabling a second hit (Trivy non-atomic rotation; Nx stale branches).
  9. AI tooling as both target and instrument (s1ngularity, Clinejection, hackerbot-claw, LiteLLM, Bitwarden payload).
- **Why security tools became the vector:** scanners run in nearly every pipeline, usually early, usually by tag, and frequently in jobs that also hold registry/cloud credentials. A scanner needs none of those secrets to do its job.
- **What would have prevented or contained each (inference from the advisories' own "not affected" lists):**
  - tj-actions/reviewdog/KICS/trivy-action: SHA pin + no secrets in the job + egress allowlist. SHA pin alone would not have saved reviewdog dependents (transitive) or old trivy-action pins.
  - Nx/hackerbot-claw: no `pull_request_target`; env-var indirection for untrusted strings; delete stale branches.
  - chalk/debug/axios/LiteLLM/Bitwarden/Shai-Hulud (as a consumer): lockfile + ≥1–7 day cooldown + install scripts disabled. All malicious versions above were live for hours, not days.
  - Shai-Hulud/GhostAction (as a publisher): no long-lived publish tokens; phishing-resistant 2FA.
  - LiteLLM Oct 2026 / Bitwarden: trusted publishing is necessary but not sufficient; the release workflow needs an environment with a required reviewer and a restriction on which repo/ref can run it.
- **Time-to-detection has shrunk to hours, which makes cooldowns disproportionately effective**, but Datadog explicitly warns patient attackers can delay payload execution past the window.

## 2. GitHub Actions hardening, concretely

### Takeaway
The highest-value free controls for a solo developer are: lock or SHA-pin every action, set `permissions:` to read-only with per-job elevation, remove `pull_request_target`, keep secrets out of any job that runs third-party tools, replace long-lived keys with OIDC and trusted publishing, and add a 7-day cooldown to every updater and package manager. Egress filtering and ephemeral runners matter most when the runner is self-hosted; a self-hosted runner on the production VM converts any of the section-1 compromises into a production compromise.

### Cited Findings

**Pinning, lockfiles and their limits**
- GitHub's secure-use doc now says "The best measure is to lock your workflow dependencies with a lockfile," which "records the exact commit for every action your workflows depend on, including transitive dependencies" and "supersedes SHA pinning for repositories that adopt it." For repos that cannot adopt it: "Pin references to actions to a commit SHA." PROMISING (new). — [github/docs secure-use](https://github.com/github/docs/blob/main/content/actions/reference/security/secure-use.md) [F]
- Lockfile specifics: path `.github/workflows/actions.lock`, generated by the `gh actions-lock` CLI extension, never hand-edited; records ref, commit SHA, `owner_id`, `repo_id`; a commit that exists only in a fork or is no longer reachable from the recorded ref is rejected at run time; satisfies the "require full-length SHA" policy. It does NOT cover reusable workflows (`jobs.<id>.uses` — pin those by SHA), inputs, secrets or the runner image. The doc is behind feature flag `actions-workflow-lockfiles`; preview/GA status and plan availability not stated. — [github/docs workflow-dependency-lockfiles](https://github.com/github/docs/blob/main/content/actions/concepts/security/workflow-dependency-lockfiles.md) [F]
- GitHub announced workflow dependency locking, scoped secrets, a native Layer-7 egress firewall for hosted runners (running outside the runner VM) and an Actions Data Stream in its 2026 Actions security roadmap (2026-03-26). Timelines in third-party summaries only. — [GitHub blog](https://github.blog/security/supply-chain-security/whats-coming-to-our-github-actions-2026-security-roadmap/) [S]
- SHA-pinning enforcement: since 2025-08-15 admins can require SHA pinning in the allowed-actions policy and maintain an action blocklist. — [GitHub changelog](https://github.blog/changelog/2025-08-15-github-actions-policy-now-supports-blocking-and-sha-pinning-actions/) [S]. Third-party note: enforcement only checks that the ref is a 40-char SHA, not who authored the commit. — [platformengineering.org](https://platformengineering.org/blog/beyond-sha-pinning-why-immutability-isnt-provenance-in-github-actions) [S]
- Immutable releases (tag and assets locked, Sigstore-signed release attestation) reported GA October 2025; this is a publisher opt-in. — [platformengineering.org](https://platformengineering.org/blog/beyond-sha-pinning-why-immutability-isnt-provenance-in-github-actions) [S]
- PROVEN limits of SHA pinning: (a) transitive actions — reviewdog dependents affected "regardless of version or pinning method" — [GHSA-qmg3-hpqr-gqvc](https://github.com/advisories/GHSA-qmg3-hpqr-gqvc) [F]; (b) pinned action that downloads an unpinned tool — trivy-action SHA pins predating 2025-04-09 and `version: latest` were affected — [Aqua advisory](https://github.com/aquasecurity/trivy/security/advisories/GHSA-69fq-xp46-6x23) [F]; (c) imposter commits from forks — Trivy's attacker swapped an `actions/checkout` reference for an imposter commit — same advisory [F]; (d) Dependabot "will not create alerts for actions pinned to SHA values" — [github/docs secure-use](https://github.com/github/docs/blob/main/content/actions/reference/security/secure-use.md) [F]

**Triggers, permissions, injection**
- GitHub: "Avoid using the `pull_request_target` workflow trigger if it's not necessary"; prefer `workflow_run` for privilege separation but treat artifacts from other workflows with caution; privileged workflows must not check out untrusted PR code. Script-injection fix: "set the value of the expression to an intermediate environment variable." Set default `GITHUB_TOKEN` to read-only and elevate per job. — [github/docs secure-use](https://github.com/github/docs/blob/main/content/actions/reference/security/secure-use.md) [F]
- Late-2025 platform change: announced 2025-11-07, `pull_request_target` workflows are always evaluated from the repository's default branch (previously the PR's target branch), closing the Nx-style "stale branch still has the vulnerable workflow" hole; environment branch-protection evaluation also changed. — [Socket](https://socket.dev/blog/github-actions-checkout-blocks-pull-request-target-checkouts) [S]; effective date 2025-12-08 is `[M]` — [GitHub changelog](https://github.blog/changelog/2025-11-07-actions-pull_request_target-and-environment-branch-protections-changes/) [M]
- `actions/checkout` v7.0.0 "Block[s] checking out fork PR for pull_request_target and workflow_run"; v6.0.0 persists credentials to a separate file. — [actions/checkout CHANGELOG](https://github.com/actions/checkout/blob/main/CHANGELOG.md) [F]. The opt-out input is `allow-unsafe-pr-checkout: true` (zizmor has a `dangerous-checkout` audit for it). — [zizmor audits](https://github.com/zizmorcore/zizmor/blob/main/docs/audits.md) [F]. Socket dated the checkout change 2026-06-20. — [Socket](https://socket.dev/blog/github-actions-checkout-blocks-pull-request-target-checkouts) [S]

**Secrets, environments, OIDC**
- "A workflow job cannot access environment secrets until approval is granted by a reviewer." Avoid structured (JSON/YAML) secrets; if a secret reaches a log, delete the log and rotate. Put `.github/workflows` under CODEOWNERS. — [github/docs secure-use](https://github.com/github/docs/blob/main/content/actions/reference/security/secure-use.md) [F]
- OIDC trust-policy pitfall: AWS role trust policies that check `aud` but omit a `sub` condition let "a GitHub Action from any GitHub repository" assume the role; researchers collected 500+ role ARNs across 275+ accounts and found a number assumable. Since June 2025 AWS blocks creation of new roles with this flaw; pre-existing roles are not fixed. Use `StringEquals` on `sub` with `repo:OWNER/REPO:ref:refs/heads/main` (or `StringLike repo:OWNER/REPO:*` at minimum) plus `aud = sts.amazonaws.com`. PROVEN. — [Datadog Security Labs (2023, updated 2025-06-18)](https://securitylabs.datadoghq.com/articles/exploring-github-to-aws-keyless-authentication-flaws/) [F]
- Trusted publishing: adopted post-incident by Nx, Cline and LiteLLM. — [Nx](https://github.com/nrwl/nx/security/advisories/GHSA-cxm3-wv7p-598c) [F]; [Cline](https://github.com/cline/cline/security/advisories/GHSA-9ppg-jx86-fqw7) [F]; [LiteLLM](https://github.com/BerriAI/litellm/issues/24512) [F]. Limits: Bitwarden CLI was reportedly published through a trusted-publishing workflow, and Mini Shai-Hulud reportedly produced validly attested malicious packages. — [The Hacker News](https://thehackernews.com/2026/04/bitwarden-cli-compromised-in-ongoing.html) [S]; [Snyk](https://security.snyk.io/TanStack-npm-Supply-Chain-Compromise-May-2026) [S]

**Egress control**
- Harden-Runner: free Community tier covers public repos on GitHub-hosted runners (egress audit, domain-allowlist blocking, global block list enforced even in audit mode, source-modification detection). Private repos and all self-hosted runners require the paid Enterprise tier — "Self-hosted runners require an Enterprise subscription, even for public repositories"; without it the action is a no-op. Linux hosted runners fully supported; Windows/macOS audit only. — [harden-runner README](https://github.com/step-security/harden-runner) [F]
- Harden-Runner's tj-actions detection: anomalous outbound call to `gist.githubusercontent.com`. PROVEN. — [GHSA-mrrh-fwg8-r2c3](https://github.com/advisories/GHSA-mrrh-fwg8-r2c3) [F]
- BullFrog: MIT-licensed, free; `egress-policy: audit|block`, `allowed-domains`, `allowed-ips`, `dns-policy`, `enable-sudo`. GitHub-hosted Ubuntu only; container jobs unsupported; root can bypass filtering (raw packets, Docker) unless `enable-sudo: false`. PROMISING. — [bullfrog README](https://github.com/bullfrogsec/bullfrog) [F]

**Self-hosted runners**
- GitHub: self-hosted runners "can be persistently compromised by untrusted code in a workflow"; should almost never be used for public repos; just-in-time runners "perform at most one job before being automatically removed," though reused hardware can still leak. — [github/docs secure-use](https://github.com/github/docs/blob/main/content/actions/reference/security/secure-use.md) [F]
- Shai-Hulud 2.0 registered victim machines as self-hosted runners (`SHA1HULUD`) to get persistent remote execution. — [Datadog](https://securitylabs.datadoghq.com/articles/shai-hulud-2.0-npm-worm/) [F]

**Cache and artifact poisoning**
- Clinejection crossed from an unprivileged triage workflow to the release workflow through a shared cache key. — [Snyk](https://snyk.io/blog/cline-supply-chain-attack-prompt-injection-github-actions) [S]. zizmor's `cache-poisoning` audit flags cache reads in release workflows and cache writes from privileged triggers; `artipacked` flags checkout credentials leaking via artifacts. — [zizmor audits](https://github.com/zizmorcore/zizmor/blob/main/docs/audits.md) [F]

**Dependency updates and package managers**
- Dependabot `cooldown`: `default-days`, `semver-major/minor/patch-days`, `include`, `exclude`; `github-actions` ecosystem supports `default-days` only; if omitted Dependabot applies 3 days by default; cooldown never applies to security updates. — [github/docs dependabot options](https://github.com/github/docs/blob/main/content/code-security/reference/supply-chain-security/dependabot-options-reference.md) [F]
- Cooldown evidence: axios found ~3h after release; s1ngularity live ~4h; a 12-hour cooldown would have blocked both; one week is the common recommendation, one day the minimum. Config: npm ≥ 11.10.0 `min-release-age=7` in `.npmrc`; pnpm `minimumReleaseAge: 10080` (minutes); Yarn `npmMinimalAgeGate: "7d"`. Caveat: attackers may delay execution past the window. PROVEN for short-lived malicious releases. — [Datadog, 2026-04-16](https://securitylabs.datadoghq.com/articles/dependency-cooldowns/) [F]
- William Woodruff: 8 of 10 analysed attacks had windows under a week. Other names: uv `exclude-newer`, pip `--uploaded-prior-to`, Renovate `minimumReleaseAge`, Deno `--minimum-dependency-age`; pnpm added the setting in 10.16 and (one source) pnpm 11 defaults to 1 day. — [Socket glossary](https://socket.dev/glossary/dependency-cooldown) [S]; [Woodruff, 2025-11-21](https://www.blog.yossarian.net/2025/11/21/We-should-all-be-using-dependency-cooldowns) [S]
- Install scripts were the execution point for Nx (`postinstall`), Shai-Hulud 2.0 (`preinstall`), Cline, axios and Bitwarden; `.pth` files were the Python equivalent for LiteLLM. — sources in section 1 [F]/[S]. pnpm ≥ 10 does not run dependency lifecycle scripts unless allowlisted. — [pnpm docs](https://pnpm.io/supply-chain-security) [M]

### Inferences
**Prioritised checklist for a solo developer (free unless noted):**

1. **Remove the blast radius first.** No self-hosted runner on the production VM. If self-hosting is unavoidable: separate VM, ephemeral/JIT one-job runners, no Docker socket shared with prod, default-deny outbound firewall at the host/VPC level, private repos only. (A runner on the prod VM means every incident in section 1 is direct code execution next to production data, and Harden-Runner will not help without a paid plan.)
2. **Secrets-free scan/lint/test jobs.** Split workflows so that jobs running third-party tools (scanners, linters, test deps) have `permissions: contents: read` and zero secrets; only a small, separately reviewed deploy job in a protected environment gets credentials. This is the one control that defeats `Runner.Worker` memory scraping.
3. **Lock or pin everything.** Adopt `actions.lock` if available on the account; otherwise full-SHA pins with version comments (pinact/zizmor), reusable workflows by SHA, container images by digest, tools by version + checksum. Turn on "require SHA pinning" in repo Actions settings.
4. **Workflow-level `permissions: {}` or `contents: read`**, elevate per job; set the repo default token to read-only; disable "Actions can create/approve PRs" unless needed.
5. **Delete `pull_request_target`** (and audit `workflow_run`, `issue_comment`); route untrusted strings through `env:`; upgrade to `actions/checkout` v7.
6. **Kill long-lived credentials.** OIDC to cloud with `sub` pinned to repo + branch/environment; npm/PyPI trusted publishing; no classic PATs; fine-grained PATs with expiry only where unavoidable; `gh auth` tokens on the laptop count as high-value secrets (LiteLLM, Oct 2026).
7. **Environments with required reviewer** for deploy/publish (on personal accounts this is free for public repos; private-repo availability depends on plan — verify).
8. **Cooldowns everywhere:** Dependabot/Renovate ≥ 7 days (security updates bypass), npm/pnpm/yarn/uv settings, pinact min-age. Commit lockfiles; `npm ci`/`pnpm install --frozen-lockfile`; `ignore-scripts=true`; `pip install --require-hashes` or `uv sync --locked`.
9. **Egress control:** public repo → Harden-Runner community (audit, then block); private repo → BullFrog with `enable-sudo: false`, or wait for/enable GitHub's native firewall; self-hosted → host firewall. Remember `github.com` on the allowlist still permits exfil-to-own-account.
10. **Static analysis in CI** (section 3), **push protection** (section 4), **CODEOWNERS on `.github/`**, branch protection/rulesets on default and release tags.
11. **Separate cache scopes** for privileged and unprivileged workflows; never restore caches in release jobs.
12. **Incident playbook:** rotate atomically (revoke all, then reissue — Trivy lesson), delete stale branches containing old workflows (Nx lesson), search own account for unexpected repos/runners (`tpcp-docs-*`, `s1ngularity-repository*`, `SHA1HULUD`).

- PROVEN: items 2, 3, 6, 8 (each maps to an advisory "not affected" statement or documented post-incident fix). PROMISING: `actions.lock`, native egress firewall, immutable releases, BullFrog. HYPE: "SHA pinning alone makes third-party actions safe" and "trusted publishing/provenance means the package is safe" — both contradicted by 2026 incidents.

### Gaps
- Could not read GitHub changelog/blog pages directly (blocked): exact GA dates for immutable releases, the `pull_request_target` effective date, the 2026 roadmap's delivery status as of November 2026 (is the native egress firewall shipped?), and whether `actions.lock` is GA or preview.
- Whether environments with required reviewers are available on private repos for GitHub Free/Pro personal accounts was not verified.
- npm registry-side changes after Shai-Hulud (classic-token revocation, short-lived granular tokens, FIDO 2FA) are known to me only from background knowledge — [GitHub blog, 2025-09-22](https://github.blog/security/supply-chain-security/our-plan-for-a-more-secure-npm-supply-chain/) [M].
- No independent measurement found of how often egress blocking breaks legitimate builds.

## 3. Static analysis tools for workflows

### Takeaway
zizmor is the best single free tool for a solo developer (broad audit set, offline-capable, and it classifies its own auto-fixes as safe vs unsafe); pair it with actionlint for correctness and pinact for pinning. Almost no tool publishes false-positive rates, and zizmor itself treats pinning and template-injection fixes as "unsafe" (review required), which is the right default for an agent.

### Cited Findings
- **zizmor** audit catalogue (fetched 2026-11-10) includes: `unpinned-uses`, `unpinned-images`, `unpinned-tools`, `impostor-commit`, `known-vulnerable-actions`, `ref-confusion`, `ref-version-mismatch`, `stale-action-refs`, `dangerous-triggers`, `dangerous-checkout`, `excessive-permissions`, `template-injection`, `github-env`, `cache-poisoning`, `artipacked`, `secrets-inherit`, `overprovisioned-secrets`, `unredacted-secrets`, `secrets-outside-env`, `bot-conditions`, `unsound-condition`, `unsound-contains`, `unsound-ternary`, `dependabot-cooldown`, `dependabot-execution`, `adhoc-packages`, `archived-uses`, `typosquat-uses`, `forbidden-uses`, `github-app`, `self-hosted-runner`, `use-trusted-publishing`, `obfuscation`, `insecure-commands`. — [zizmor audits.md](https://github.com/zizmorcore/zizmor/blob/main/docs/audits.md) [F]
- zizmor fix safety (its own classification): **safe** (`--fix`): `bot-conditions`, `dependabot-cooldown`, `impostor-commit`, `unsound-condition`. **Unsafe** (`--fix=all`): `unpinned-uses`, `template-injection`, `artipacked`, `cache-poisoning`, `known-vulnerable-actions`, `ref-version-mismatch`, `insecure-commands`, `obfuscation`, `self-repository`, `dependabot-execution`. **No auto-fix:** `dangerous-triggers`, `excessive-permissions`, `secrets-inherit`, `github-env`, `overprovisioned-secrets`, and others. Only four audits need network/GitHub API (`impostor-commit`, `known-vulnerable-actions`, `ref-confusion`, `stale-action-refs`); the rest run offline. — [zizmor audits.md](https://github.com/zizmorcore/zizmor/blob/main/docs/audits.md) [F]
- **poutine** (BoostSecurity, Apache-2.0): detects build-pipeline misconfigurations (untrusted-code execution, `unpinnable_action`, `pr_runs_on_self_hosted`, unverified-creator actions, known build-platform CVEs); GitHub Actions, GitLab, Azure DevOps, Tekton; pretty/JSON/SARIF; custom Rego rules; org-wide scan; no auto-fix mentioned; checks for new releases over the network at most once per 24h by default (can be disabled). — [poutine README](https://github.com/boostsecurityio/poutine) [F]
- **OpenSSF Scorecard** checks and stated limits: Dangerous-Workflow (Critical) "does not detect whether untrusted code checkouts are used safely"; Token-Permissions (High) cannot see the repo-level read-only setting; Pinned-Dependencies (Medium); Branch-Protection needs an admin token for several settings; Signed-Releases "does not verify the signatures"; Dependency-Update-Tool only checks the tool is enabled. — [scorecard checks.md](https://github.com/ossf/scorecard/blob/main/docs/checks.md) [F]
- **StepSecurity secure-repo** (AGPL-3.0): auto-generates PRs for minimum `GITHUB_TOKEN` permissions (from a knowledge base of known actions), SHA-pinning, Docker digest pinning, adding Harden-Runner and Dependabot config; hosted flow is for public repos. — [secure-repo README](https://github.com/step-security/secure-repo) [F]
- **Gato-X** (Apache-2.0): offensive/enumeration tool for pwn requests, Actions injection, TOCTOU and self-hosted-runner takeover with reachability and gate-check analysis; states it "will have a higher false positive rate than SAST tools like CodeQL" because it is tuned against false negatives; attack features require authorisation. — [gato-x README](https://github.com/AdnaneKhan/gato-x) [F]
- **pinact** (MIT): pins actions and reusable workflows to SHAs; `--check` for CI; `--update` with a configurable minimum release age; `--verify-comment` because "a version comment isn't necessarily true"; aware of `.github/workflows/actions.lock` and pins the reusable workflows the lockfile does not cover. — [pinact README](https://github.com/suzuki-shunsuke/pinact) [F]
- **actionlint** (syntax/type checking, shellcheck/pyflakes integration, untrusted-input expression checks), **Octoscan** (Synacktiv), **ratchet** (sethvargo) and **frizbee** (Stacklok) — not fetched this session. — [actionlint](https://github.com/rhysd/actionlint) [M]; [octoscan](https://github.com/synacktiv/octoscan) [M]; [ratchet](https://github.com/sethvargo/ratchet) [M]; [frizbee](https://github.com/stacklok/frizbee) [M]

### Inferences
- Suggested minimal stack: `actionlint` + `zizmor` (offline mode in a no-network sandbox, plus a separate online pass for the four API audits) + `pinact --check`. Add `poutine` if GitLab/Tekton are in scope. Run Scorecard weekly for public repos only.
- For an agent: auto-apply only zizmor "safe" fixes; turn "unsafe" fixes into PRs with the diff and the upstream tag↔SHA evidence; never auto-fix `dangerous-triggers`/`excessive-permissions` (no tool offers a fix because the right answer depends on intent).
- Pinning tools resolve tag→SHA at the moment they run; running one during a tag-hijack window pins the malicious commit. Combine with a min-age check and `impostor-commit`/`ref-version-mismatch` audits.

### Gaps
- No published false-positive/precision figures found for zizmor, poutine, actionlint or Octoscan. I believe a 2026 arXiv comparison of GitHub Actions security scanners exists but could not reach arxiv.org to confirm title or numbers.
- actionlint, Octoscan, ratchet and frizbee capabilities are `[M]` only.

## 4. Secret scanning

### Takeaway
Run a verifying scanner (TruffleHog, or gitleaks for speed) locally and in CI, enable GitHub push protection wherever the plan allows, and treat any exposure as "rotate first, clean up second". Attackers now run the same scanners on victims' machines.

### Cited Findings
- TruffleHog (AGPL-3.0 since v3): 800+ secret types, 700+ detectors with live verification; result states `verified` (confirmed active by API call), `unverified`, `unknown` (verification errored); `--results=verified,unknown`, `--fail` (exit 183); GitHub Action needs `fetch-depth: 0`; can scan a whole org with `trufflehog github --org`. — [trufflehog README](https://github.com/trufflesecurity/trufflehog) [F]
- Shai-Hulud 2.0 downloaded TruffleHog onto victims to find credentials. — [Datadog](https://securitylabs.datadoghq.com/articles/shai-hulud-2.0-npm-worm/) [F]
- GitHub guidance on exposure: delete the log and rotate the secret; register transformed (e.g., base64) values so they are masked; avoid structured secrets because redaction can fail. — [github/docs secure-use](https://github.com/github/docs/blob/main/content/actions/reference/security/secure-use.md) [F]
- Rotation over deletion, PROVEN: tj-actions advisory instructs revoking and rotating any secret that could have been exposed in the window; Aqua's advisory attributes the March 19 compromise to rotation that "was not atomic". — [GHSA-mrrh-fwg8-r2c3](https://github.com/advisories/GHSA-mrrh-fwg8-r2c3) [F]; [Aqua advisory](https://github.com/aquasecurity/trivy/security/advisories/GHSA-69fq-xp46-6x23) [F]
- GitHub secret scanning and push protection are free on public repositories; for private repositories they require the paid GitHub Secret Protection product (unbundled 2025-04-01, list price $19 per active committer/month, purchasable on Team and Enterprise plans). — [GitHub changelog 2025-03-04](https://github.blog/changelog/2025-03-04-introducing-github-secret-protection-and-github-code-security/) [M]
- gitleaks (MIT, regex + entropy, fast, pre-commit friendly, no live verification) and detect-secrets (Yelp; baseline-file workflow suited to legacy repos). — [gitleaks](https://github.com/gitleaks/gitleaks) [M]; [detect-secrets](https://github.com/Yelp/detect-secrets) [M]
- Canary tokens (e.g., Thinkst Canarytokens AWS-key tokens) alert when a planted credential is used. — [canarytokens.org](https://canarytokens.org/) [M]

### Inferences
- For a solo dev with private repos on a personal plan, GitHub-native push protection is likely unavailable, so a local pre-commit hook (gitleaks) plus a CI job (TruffleHog `--results=verified,unknown --fail`) is the free substitute.
- Canary tokens in CI are PROMISING: planting a canary cloud key as a secret in every job that runs third-party code would have fired on the tj-actions/Trivy/KICS memory scrapers once the attacker tested the keys. No source measuring this in CI was found.
- Post-leak order of operations: revoke all → reissue → audit provider logs for use during the window → then purge logs/history. Purging history without rotation is not remediation.
- Verification makes outbound calls with the candidate secret; in a default-deny sandbox run TruffleHog with `--no-verification` or allowlist only the provider APIs.

### Gaps
- GitHub docs pages on secret-scanning availability returned HTTP 503; plan/pricing details are `[M]` only and should be re-checked, including whether personal Pro accounts can buy Secret Protection.
- No comparative precision/recall data for gitleaks vs TruffleHog vs detect-secrets retrieved.

## 5. SBOM, signing and provenance

### Takeaway
For a solo developer deploying to one VM, the useful subset is: generate an SBOM per build, sign/attest the image, deploy by digest, and verify identity at deploy time. SLSA Build L2 comes almost for free on GitHub-hosted runners; L3 requires isolating the build in a reusable workflow. Provenance proves where something was built, not that it is benign — the Trivy v0.69.4 binary came out of the project's own release pipeline.

### Cited Findings
- GitHub artifact attestations: Sigstore-based; public repos use the Sigstore public-good instance (bundle also written to a public transparency log), private repos use GitHub's Sigstore instance (no transparency log). Attestations alone give SLSA v1.0 Build Level 2; building in a reusable workflow isolated from the caller can meet Build Level 3. Verify with `gh attestation verify`. "Not a guarantee that an artifact is secure." — [github/docs artifact-attestations](https://github.com/github/docs/blob/main/content/actions/concepts/security/artifact-attestations.md) [F]
- Availability: public repos on all plans; private/internal repos require GitHub Enterprise Cloud. — [GitHub docs](https://docs.github.com/en/actions/security-for-github-actions/using-artifact-attestations/using-artifact-attestations-to-establish-provenance-for-builds) [M]
- Consuming scanners safely after Trivy (PROVEN from the advisory's unaffected list): digest-referenced images, source builds, the Homebrew formula and SHA-pinned safe commits were unaffected; Aqua recommends verifying installs with cosign against Sigstore signatures and Rekor timestamps (v0.69.2 artifacts signed 2026-03-01). — [Aqua advisory](https://github.com/aquasecurity/trivy/security/advisories/GHSA-69fq-xp46-6x23) [F]
- The malicious v0.69.4 was produced by tagging a release after pushing a commit that altered the build (imposter `actions/checkout`, `--skip=validate`), then distributed via GHCR, ECR Public, Docker Hub, deb/rpm and get.trivy.dev. — [Aqua advisory](https://github.com/aquasecurity/trivy/security/advisories/GHSA-69fq-xp46-6x23) [F]
- Scorecard's Signed-Releases check only looks for signature files and "does not verify the signatures". — [scorecard checks.md](https://github.com/ossf/scorecard/blob/main/docs/checks.md) [F]
- Mini Shai-Hulud reportedly published validly attested malicious npm packages. — [Snyk](https://security.snyk.io/TanStack-npm-Supply-Chain-Compromise-May-2026) [S]
- LiteLLM began cosigning releases after March 2026. — [LiteLLM issue](https://github.com/BerriAI/litellm/issues/24512) [F]
- SLSA: v1.0 defines Build L1 (provenance exists), L2 (hosted build platform, signed provenance), L3 (hardened, isolated builds; non-forgeable provenance); v1.1 and v1.2 followed, v1.2 adding a Source track. — [slsa.dev v1.0 levels](https://slsa.dev/spec/v1.0/levels) [M]; [slsa.dev v1.2](https://slsa.dev/spec/v1.2/) [M]
- Tools: Syft (SBOM generation, SPDX and CycloneDX), Grype and OSV-Scanner (vulnerability matching), cosign keyless (`cosign verify --certificate-identity … --certificate-oidc-issuer https://token.actions.githubusercontent.com`), Sigstore policy-controller (Kubernetes admission). — [syft](https://github.com/anchore/syft) [M]; [grype](https://github.com/anchore/grype) [M]; [osv-scanner](https://github.com/google/osv-scanner) [M]; [Sigstore docs](https://docs.sigstore.dev/cosign/verifying/verify/) [M]

### Inferences
- **Safe scanner consumption recipe:** download a specific release binary (not `latest`, not a setup action), verify SHA-256 against a value committed in the repo and verify the cosign signature/identity, require the release to be ≥ 7 days old, vendor or cache it in your own registry/bucket, and run it in a job or container with no secrets, read-only source mount and no network (pre-fetch the vulnerability DB in a separate step, or allowlist only the DB host). Prefer two independent scanners over one (e.g., Grype + OSV-Scanner) so a single compromised vendor is neither a single point of failure nor of trust.
- **Signature + cooldown + digest pin together** would have blocked v0.69.4; signature alone probably would not, since the release came through the legitimate pipeline (inference from the advisory's emphasis on Rekor timestamps).
- **SLSA for a solo dev:** Build L2 on GitHub-hosted runners is PROVEN-cheap (one `actions/attest-build-provenance` step on public repos; cosign keyless for private repos on non-Enterprise plans). Build L3 is achievable by moving the build into a reusable workflow, but its marginal value for a one-person project deploying to one VM is low — PROMISING at best, bordering on HYPE if pursued before checklist items 1–8 in section 2. The Source track mostly formalises branch protection and review, which a solo developer cannot fully satisfy (no second reviewer).
- **Deploy-time verification on a single VM:** policy-controller is Kubernetes-only and overkill. A deploy script that (1) resolves the image digest, (2) runs `cosign verify` or `gh attestation verify oci://… --repo OWNER/REPO` pinned to the expected workflow identity, and (3) runs `docker pull image@sha256:…` only on success, gives the same guarantee. The verification must run on the VM (or a deploy host), not in the pipeline that produced the artifact.

### Gaps
- slsa.dev unreachable; v1.1/v1.2 release dates and the exact Source-track level requirements are unverified. The `slsa-framework/slsa` GitHub releases page lists no releases.
- Private-repo availability of artifact attestations is `[M]`; the fetched concept page describes the private Sigstore instance but not plan gating.
- Could not confirm from a primary source whether trivy v0.69.4 carried a valid cosign signature.
- Syft/Grype/OSV-Scanner/cosign specifics are `[M]` only.

## 6. AI agents diagnosing and fixing CI

### Takeaway
Products exist (Copilot coding agent, GitHub Agentic Workflows, Claude Code Action, vendor "fix my pipeline" features) but I found no independent success-rate measurements for them; the only quantified result I can cite is an industrial paper from memory. The security evidence, by contrast, is concrete: AI steps in CI have already been the entry point for a real npm compromise, and malware has used local AI CLIs for reconnaissance.

### Cited Findings
- **PromptPwnd (Aikido, early December 2025):** vulnerability class where untrusted issue/PR/commit text is embedded into the prompt of an AI agent that holds a powerful token and tools. Named integrations: Gemini CLI, Claude Code, OpenAI Codex, GitHub AI Inference; Gemini CLI's own workflow was the demonstrated case. Mitigations: restrict agent tools, avoid tools that can write to issues/PRs, sanitise untrusted input. — [Aikido](https://aikido.dev/blog/promptpwnd-github-actions-ai-agents) [S]; [CSO Online](https://csoonline.com/article/4101751/ai-in-ci-cd-pipelines-can-be-tricked-into-behaving-badly-2.html) [S]. A Cloud Security Alliance research note (2026-05-03) covers the same class. — [CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-ai-github-actions-security-20260503-csa-st/) [S]
- **Clinejection (Feb 2026):** issue-title prompt injection → AI triage workflow runs attacker code → shared cache → release workflow → unauthorised npm publish. PROVEN real-world chain. — [Snyk](https://snyk.io/blog/cline-supply-chain-attack-prompt-injection-github-actions) [S]; [Cline advisory](https://github.com/cline/cline/security/advisories/GHSA-9ppg-jx86-fqw7) [F]
- **claude-code-action security doc:** only users with write access can trigger by default; `allowed_non_write_users` "is a significant security risk and should only be used for workflows with extremely limited permissions"; "Do not use a personal access token — a static token … could be partially or fully recovered over time via prompt injection"; restrict tools via `--allowedTools`; subprocess env scrubbing "reduces but does not eliminate prompt injection risk"; `allowed_bots` are not permission-checked; for `pull_request_target`/`workflow_run`, "Do not check out an untrusted ref into the workspace root before this action"; on PRs it restores `.claude/`, `.mcp.json`, `CLAUDE.md`, `.husky/` from the base branch but `package.json`, lockfiles and `Makefile` stay PR-controlled; Claude does not open PRs itself by default — "the user must click the link and create the PR themselves, ensuring human oversight"; `show_full_output` is off by default because logs are public. — [claude-code-action security.md](https://github.com/anthropics/claude-code-action/blob/main/docs/security.md) [F]
- **GitHub Agentic Workflows (`gh-aw`):** Markdown-defined agent workflows compiled to Actions YAML with a `.lock.yml`; "Agent jobs are read-only and sandboxed by default"; writes go through validated `safe-outputs` jobs with scoped permissions. Releases `>= 0.83.3, < 0.85.4` were retired after a security vulnerability. — [gh-aw README](https://github.com/github/gh-aw) [F]
- **Malware using AI CLIs:** s1ngularity invoked Claude Code, Gemini CLI and Amazon Q with permission-bypass flags to hunt secrets. — [Snyk](https://snyk.io/blog/weaponizing-ai-coding-agents-for-malware-in-the-nx-malicious-package) [S]. Later payloads reportedly tamper with AI-assistant configuration and persist in Claude Code/VS Code settings. — [Security Boulevard](https://securityboulevard.com/2026/04/the-butlerian-jihad-compromised-bitwarden-cli-deploys-npm-worm-poisons-ai-assistants-and-dumps-github-secrets) [S]; [Snyk](https://security.snyk.io/TanStack-npm-Supply-Chain-Compromise-May-2026) [S]
- **AI on offence:** hackerbot-claw automated discovery and exploitation of vulnerable workflows over ~9 days. — [StepSecurity](https://stepsecurity.io/blog/hackerbot-claw-github-actions-exploitation) [S]
- **LogSage (ByteDance, arXiv 2506.03691, 2025):** LLM framework for CI/CD failure root-cause analysis and remediation; reports >98% root-cause precision on a curated benchmark and >80% end-to-end precision over ~1.07M production executions. PROMISING; single-vendor, self-reported, recalled from memory. — [arXiv](https://arxiv.org/abs/2506.03691) [M]
- **Copilot coding agent guardrails:** runs in an ephemeral Actions environment behind a firewall with an allowlist, can push only to its own `copilot/*` branches, and workflows on its PRs need human approval to run. — [GitHub docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent) [M]

### Inferences
- Recommended guardrails, derived from the incidents and vendor docs above:
  1. Never feed attacker-controllable text (issue/PR titles and bodies, commit messages, branch names, logs from fork builds, dependency READMEs) into an agent that holds a write token; when unavoidable, the agent must be read-only with output through a validated "safe output" step.
  2. The diagnosing agent and the acting step are separate jobs with separate tokens (gh-aw model).
  3. Short-lived `GITHUB_TOKEN` only; no PATs; no `workflows`/`contents: write` unless the run was triggered by the repo owner.
  4. Tool allowlists rather than free shell; no network except the model API and GitHub.
  5. No shared caches between AI jobs and release jobs.
  6. Agent output is a PR a human merges.
  7. Treat CI logs as untrusted input: a failing job's log can contain injected instructions.
- For a self-hosted agent the safer architecture is to run it **outside** GitHub Actions (on its own sandboxed host), reading run logs via a read-only token and proposing PRs via a narrowly scoped GitHub App, rather than as a workflow step triggered by repository events.
- "AI auto-fixes your pipeline" success-rate claims from vendors are HYPE until independently measured; failure classes that are plausibly tractable (PROMISING) are mechanical ones: flaky re-runs, lockfile drift, deprecated action versions, missing permissions scopes, cache misses.

### Gaps
- No independent, published success rates found for Copilot coding agent, gh-aw, Claude Code Action, GitLab Duo, CircleCI or Dagger CI-fix features (search budget exhausted before this topic; vendor sites blocked).
- LogSage figures and Copilot guardrail details are `[M]`; arxiv.org and docs.github.com were unreachable. CI-repair benchmark results for 2025–2026 (e.g., JetBrains Long Code Arena "CI builds repair") could not be retrieved.
- Aikido's original post, its Gemini CLI fix timeline and the "at least 6 Fortune 500 companies" figure were not read directly.
- gh-aw's preview/GA status and network-firewall details are not stated on the README.

## 7. Proposed change-authority policy for an agent acting on pipelines

### Takeaway
Ground the policy in three published facts: GitHub tells humans to gate workflow changes behind CODEOWNERS review and environment approval; zizmor classifies pinning and injection fixes as "unsafe" (review needed); and every 2026 cascade started from a workflow or credential change nobody reviewed. So the agent's default is "propose via PR"; only reversible, non-semantic, mechanically verifiable actions are automatic; anything touching secrets, triggers, deploy paths or protections needs approval; weakening a control to get green is never allowed.

### Cited Findings
- GitHub: add `.github/workflows` to CODEOWNERS so changes "first require approval from a designated reviewer"; environment secrets are unavailable "until approval is granted by a reviewer"; avoid `pull_request_target`; keep `GITHUB_TOKEN` read-only by default. — [github/docs secure-use](https://github.com/github/docs/blob/main/content/actions/reference/security/secure-use.md) [F]
- zizmor marks `unpinned-uses`, `template-injection`, `cache-poisoning`, `artipacked`, `known-vulnerable-actions` fixes as unsafe and offers no auto-fix for `dangerous-triggers` or `excessive-permissions`. — [zizmor audits.md](https://github.com/zizmorcore/zizmor/blob/main/docs/audits.md) [F]
- claude-code-action's default: the agent commits to a branch and a human creates the PR. — [security.md](https://github.com/anthropics/claude-code-action/blob/main/docs/security.md) [F]
- gh-aw's default: read-only agent, writes only via validated safe-output jobs. — [gh-aw README](https://github.com/github/gh-aw) [F]
- Dependabot: cooldown applies to version updates, not security updates. — [dependabot options](https://github.com/github/docs/blob/main/content/code-security/reference/supply-chain-security/dependabot-options-reference.md) [F]
- Incident precedents: unreviewed workflow merged → Nx; non-atomic rotation → Trivy; release workflow runnable from a look-alike fork with developer tokens → LiteLLM Oct 2026; shared cache → Cline. — sources in section 1 [F]/[S]

### Inferences
**Tier 0 — automatic, no PR (read-only or trivially reversible)**
- Read logs, run linters/scanners in the sandbox, compute diagnoses, open/annotate issues.
- Re-run a failed job, at most N times (suggest 2), only when the failure matches a known-flaky signature and the triggering commit is the owner's; record every re-run.
- Cancel a run that is exhibiting exfil indicators (unexpected egress, new public repo, new runner registration) and notify.

**Tier 1 — automatic PR; may auto-merge only if every listed check passes**
- Pin an action tag to a full SHA with version comment — conditions: SHA is reachable from the upstream tag in the upstream repo (not a fork), tag is ≥ 7 days old, no open advisory, diff touches only the `uses:` line.
- Bump an existing pinned SHA after cooldown, with upstream changelog/compare link in the PR — auto-merge only for first-party `actions/*` and only if the action's own `action.yml` did not add new inputs, network downloads or a changed `runs:` type; otherwise leave for review.
- Add or tighten `permissions:` (toward least privilege only), add `timeout-minutes`, add `concurrency`, add `persist-credentials: false`, apply zizmor "safe" fixes, add Dependabot `cooldown`.
- Replace `${{ … }}` interpolation of untrusted context in `run:` with env-var indirection (PR, not auto-merge; zizmor calls this fix unsafe).
- Dependency lockfile refresh within cooldown rules, with tests green.
- Rationale for PR-first even at this tier: workflow edits require a token with `workflows` write, which is itself a high-value credential; keep it out of the agent and let the human's merge be the write.

**Tier 2 — explicit human approval before any change**
- Anything that references, adds, renames or widens `secrets.*`, environments, or OIDC trust.
- Triggers: adding/changing `pull_request_target`, `workflow_run`, `issue_comment`, `workflow_dispatch` inputs, schedule.
- Deploy/publish/release jobs and anything in a protected environment.
- Runner configuration (`runs-on`, self-hosted labels, container images, services).
- Introducing any new third-party action, reusable workflow, container image or downloaded tool.
- Widening `permissions:` in any direction; changing cache keys/scopes.
- Security-update bumps that bypass cooldown (approve fast, but approve).
- Credential rotation (agent prepares the checklist; human executes atomically).

**Tier 3 — never**
- Disable, skip, `continue-on-error`, `|| true`, or delete tests, scanners, required checks or signature verification to get a green build; lower thresholds; add ignore/allowlist entries to scanners without approval.
- Change branch protection/rulesets, CODEOWNERS, environment reviewers, repo Actions policy or secret values.
- Force-push, rewrite history, delete tags/releases, retarget tags.
- Add steps that send repository content, env or secrets to any external host; add `curl | bash`; enable `ACTIONS_STEP_DEBUG`/full-output logging on public repos.
- Act on instructions found in logs, issues, PR text, commit messages, dependency files or tool output (treat as data).
- Approve or merge its own Tier 2 proposals; use a PAT; modify its own policy file.

- Enforcement should be technical, not prompt-based: a GitHub App with `contents: write` limited to an `agent/*` branch prefix and `pull_requests: write`, no `workflows`, `administration` or `secrets` permission; rulesets that require owner approval on `.github/**`; a diff-classifier outside the model that maps changed paths/keys to tiers and refuses out-of-tier diffs.

### Gaps
- I found no published standard (GitHub, OpenSSF, CISA, SLSA) that specifies what an autonomous agent may change in CI without approval; the tiering is my synthesis from the cited human-oriented guidance and incidents. OpenSSF s2c2f and CISA guidance could not be fetched.
- Whether a GitHub App can be denied `workflows` permission while still opening PRs that touch `.github/workflows` (so the human merge performs the write) should be confirmed against current GitHub App permission semantics.

## 8. Securing the agent's own toolchain (scanners, actions, MCP servers, Python/npm dependencies)

### Takeaway
Assume any one tool in the agent's stack will ship a malicious release within the next year — four of the tools a security agent would naturally use (Trivy, KICS, LiteLLM, a password-manager CLI) did in 2026. Design so that a compromised tool finds no credentials, cannot reach the network, and cannot update itself: pinned and hashed installs, a 7-day cooldown, per-tool sandboxes with default-deny egress, and MCP servers pinned by version and by tool-description hash.

### Cited Findings
- Tools that were unaffected in the Trivy incident were those consumed by digest, by known-good SHA, from source, or via a slower third-party channel (Homebrew). — [Aqua advisory](https://github.com/aquasecurity/trivy/security/advisories/GHSA-69fq-xp46-6x23) [F]
- Python-specific persistence: `.pth` and `sitecustomize.py` files execute on every interpreter start and survive `pip uninstall`; Datadog's guidance is "Do not treat reverting the compromised packages as a complete remediation. Rebuild … from known-good images with pinned dependencies." — [Datadog Oct 2026](https://securitylabs.datadoghq.com/articles/litellm-compromised-pypi-docker/) [F]; [Datadog Mar 2026](https://securitylabs.datadoghq.com/articles/litellm-compromised-pypi-teampcp-supply-chain-campaign/) [F]
- Lockfile users were reported protected in the March LiteLLM incident. — [Comet](https://www.comet.com/site/blog/litellm-supply-chain-attack/) [S]
- Cooldown evidence and settings (npm `min-release-age`, pnpm `minimumReleaseAge`, Yarn `npmMinimalAgeGate`, Dependabot `cooldown`). — [Datadog](https://securitylabs.datadoghq.com/articles/dependency-cooldowns/) [F]
- LiteLLM's October 2026 compromise came through developers' GitHub CLI OAuth tokens. — [Datadog](https://securitylabs.datadoghq.com/articles/litellm-compromised-pypi-docker/) [F]
- Scanners that phone home: poutine checks for new releases by default (disableable); Snyk Agent Scan (formerly Invariant `mcp-scan`) sends MCP server configs, tool names and descriptions to the Agent Scan API and requires a `SNYK_TOKEN`; TruffleHog verification calls provider APIs with candidate secrets. — [poutine](https://github.com/boostsecurityio/poutine) [F]; [snyk/agent-scan](https://github.com/invariantlabs-ai/mcp-scan) [F]; [trufflehog](https://github.com/trufflesecurity/trufflehog) [F]
- zizmor runs fully offline except four audits. — [zizmor audits.md](https://github.com/zizmorcore/zizmor/blob/main/docs/audits.md) [F]
- Advisory monitoring blind spot: Dependabot does not alert on SHA-pinned actions; the KICS action repo published no repository advisory. — [github/docs secure-use](https://github.com/github/docs/blob/main/content/actions/reference/security/secure-use.md) [F]; [KICS advisories page](https://github.com/Checkmarx/kics-github-action/security/advisories) [F]
- MCP supply chain, PROVEN: `postmark-mcp` turned malicious in version 1.0.16 after earlier clean versions (a "rug pull" by update). — [The Hacker News](https://thehackernews.com/2025/09/first-malicious-mcp-server-found.html) [S]
- MCP tool poisoning and rug pulls (Invariant Labs, April 2025): malicious instructions hidden in tool descriptions that the model sees and the user does not; a server can change a tool description after the user approved it; one server's description can shadow another server's tools. A later "toxic agent flow" demonstration used a malicious public GitHub issue to make an agent with the GitHub MCP server leak private-repo data. — [Invariant Labs](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks) [M]; [Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability) [M]
- MCP specification security best practices cover confused-deputy, token passthrough ("MUST NOT accept any tokens that were not explicitly issued for the MCP server"), session hijacking, and in later revisions local-server compromise (show the exact command before running, sandbox with minimal privileges) and scope minimisation. — [MCP spec](https://modelcontextprotocol.io/specification/2025-06-18/basic/security_best_practices) [M]. OWASP also runs an MCP Top 10 project. — [OWASP](https://owasp.org/www-project-mcp-top-10/) [M]
- `mcp-remote` CVE-2025-6514 (JFrog, July 2025): OS command injection when connecting to a malicious MCP server. — [JFrog](https://jfrog.com/blog/2025-6514-critical-mcp-remote-rce-vulnerability/) [M]

### Inferences
**Concrete design for the agent's toolchain:**

1. **Minimise.** Each dependency is a publisher you trust with code execution. Prefer single static binaries (zizmor, gitleaks, grype, osv-scanner, cosign) over Python/npm tools with deep trees; call model APIs with a thin HTTP client rather than an aggregator proxy if only one or two providers are used (LiteLLM was compromised twice in seven months).
2. **Pin and hash.** Python: `uv lock` + `uv sync --locked` (or `pip --require-hashes`); npm: committed lockfile, `npm ci --ignore-scripts`; binaries: version + SHA-256 committed in the repo + cosign/minisign/GPG verification where upstream signs; containers by `@sha256:` digest. Build the agent image once, deploy that image; never `pip install`/`npx` at runtime.
3. **Cooldown.** Nothing newer than 7 days enters the build (`exclude-newer`, `min-release-age`, Dependabot/Renovate cooldown, pinact min-age). Security fixes are fast-tracked by a human, not automatically.
4. **Mirror/vendor.** Keep verified copies of binaries, wheels and vulnerability DBs in your own bucket/registry so a build never fetches directly from upstream and a yanked or replaced upstream artifact is detectable by hash mismatch.
5. **Sandbox per tool.** Each third-party tool runs in its own container/gVisor/bubblewrap sandbox: read-only mount of the target repo, tmpfs scratch, no environment secrets, no Docker socket, no cloud metadata endpoint, non-root, default-deny egress with a per-tool allowlist (most scanners need none after DB pre-fetch). Disable phone-home/version checks. The orchestrator, not the tool, holds credentials, and passes results as files.
6. **Credential hygiene on the host.** No long-lived `gh` OAuth token, npm token, PyPI token, cloud keys or SSH agent in the environment where tools run; use a GitHub App with short-lived installation tokens minted by the orchestrator only at the moment of a Tier 1 action.
7. **Monitor the tools themselves.** Daily job: query OSV/GHSA for every pinned tool, action and package; run zizmor's `known-vulnerable-actions` online audit; subscribe to release/security feeds of each tool's repo; because some vendors publish no advisory (KICS), also watch one or two vendor research feeds. On a hit: freeze updates, assume exposure for the window, rotate.
8. **MCP servers.** Pin exact version and artifact hash; run locally from the vendored copy (never `npx -y some-mcp@latest`); prefer first-party servers; one sandbox per server with only that server's credential, scoped read-only where possible; at start-up, hash every tool name + description + input schema and compare to an approved manifest — on any change, refuse to load until a human re-approves (this is the rug-pull control; implement it locally rather than sending descriptions to a third-party scanning API); do not mix a server that reads untrusted content with a server that can write or exfiltrate in the same agent context ("toxic flow").
9. **Self-update is Tier 2.** The agent may open a PR bumping its own dependency after cooldown; it may not merge or deploy it.
10. **Detection.** Canary credentials inside each sandbox; egress-deny logs alert on any attempted connection; alert on new public repos, new self-hosted runners or new deploy keys in the GitHub account.

- PROVEN: pin + hash + digest (Trivy unaffected list), lockfiles (LiteLLM), cooldown (Datadog), no long-lived dev tokens (LiteLLM Oct 2026). PROMISING: tool-description hashing for MCP, canaries, per-tool sandboxes (sound, but I found no incident report quantifying them). HYPE: relying on an "MCP security scanner" or on package provenance badges as the primary defence.

### Gaps
- MCP specification pages, Invariant Labs posts, OWASP MCP Top 10 and the JFrog CVE write-up were not reachable; all MCP guidance beyond the postmark-mcp incident and the Snyk Agent Scan README is `[M]`. Any "MCP security guidance 2026" published after my knowledge cutoff was not retrieved.
- The current Snyk Agent Scan README no longer documents a tool-pinning/hash feature (earlier `mcp-scan` versions did, from memory); whether any maintained open-source tool performs local tool-description pinning was not established.

- Signature-verification specifics for each recommended binary (which projects sign with cosign vs minisign vs GPG) were not checked tool by tool.
