## 1. Sensors compared for a single small VM (what each sees, overhead, content, health, blind spots)

### Takeaway
There is no rigorous, independent 2025–2026 head-to-head benchmark of Falco vs Tetragon vs Tracee; published numbers are vendor claims or low-quality blog tables, so "eBPF sensor = ~1–3% CPU and 100–400 MB RAM" is PROMISING, not PROVEN, and must be measured on the target VM. What IS proven: every syscall-hooking sensor (Falco, default Tetragon, auditd-style) has documented blind spots (io_uring, TOCTOU on arguments, root-level map/sensor tampering), Wazuh's manager+indexer does not fit a 4–8 GB VM shared with apps, and network IDS (Suricata/Zeek) costs hundreds of MB to GBs for little value on one host.

### Cited Findings

**eBPF runtime sensors (Falco / Tetragon / Tracee) — overhead**
- No rigorous independent head-to-head benchmark was found; a 2026 comparison guide gives only rough ranges (not measurements): Falco 1–3% CPU and 150–300 MB RAM per node; Tracee 1–3% CPU and 200–400 MB; Tetragon 1–4% CPU (no RAM figure). **PROMISING** (unmeasured ranges) — [Container Runtime Security 2026 guide](https://kubernetes-ae-v2.pages.dev/container-runtime-security-2026/)
- Several DEV Community posts give precise-looking numbers (e.g. Falco 0.38 modern eBPF "0.8% avg CPU", "~12 MB idle", Tracee 0.21 "37% less eBPF memory than Tetragon 1.0") with no reproducible methodology; the search tool itself flagged them as unreliable. **HYPE** — [dev.to Falco 0.38 vs Sysdig](https://dev.to/johalputt/deep-dive-falco-038s-ebpf-probe-vs-sysdig-20-kernel-module-security-internals-elp); [dev.to Tetragon 1.0 vs Tracee 0.21](https://dev.to/johalputt/cilium-tetragon-10-vs-tracee-021-for-runtime-security-observability-on-arm64-nodes-4k6m)
- Isovalent's Tetragon 1.0 launch (2023) claims "near baseline overhead and minimal resource utilization" and points to a benchmark page; the numbers were not retrievable here. A third-party "<1% for process execution monitoring" figure has no source. **PROMISING** (vendor claim) — [Isovalent press release](https://prnewswire.com/news-releases/isovalent-creators-of-ebpf-and-cilium-launch-tetragon-high-performance-kernel-based-kubernetes-security-301973670.html)
- Falco's modern eBPF probe has been an official driver since Falco 0.35.0, originally required kernel ≥5.8, needs BPF ring buffer + BTF, allocates one ring buffer per two CPUs by default (tunable via `modern_bpf.cpus_for_each_syscall_buffer` — fewer buffers = less memory, more drops), and Falco needs at minimum CAP_SYS_RESOURCE and CAP_SYS_PTRACE. **PROVEN** (official) — [Falco blog: modern eBPF probe](https://falco.org/blog/falco-modern-bpf-0-35-0/)
- Measuring eBPF program CPU for Falco is itself hard because Falco uses tail calls, which makes per-program attribution difficult — a reason published "Falco CPU%" figures are untrustworthy. — [Inspektor Gadget: measuring CPU usage of eBPF programs](https://hn.jakechampion.name/reader/https://www.inspektor-gadget.io/blog/2022/10/measuring-cpu-usage-of-ebpf-programs-with-inspektor-gadget)
- A Sept 2026 arXiv paper re-implemented four real Falco and Tetragon rules as in-kernel stateful policies and notes Falco rules are "intrinsically alert-only and operate on a single hook" (they observe syscalls after the kernel executed them), and that some cross-hook correlations cannot be expressed in one Tetragon policy (search summary). — [Enforcement of In-Kernel Stateful Security Policies via eBPF, arXiv 2609.13930](https://arxiv.org/pdf/2609.13930)
- Falco is detection-only: it "does not block syscalls pre-execution". — [Sysdig: detect CVE-2025-22224 with Falco](https://sysdig.com/blog/detect-cve-2025-22224-with-falco)

**auditd (+ laurel, go-audit, auditbeat, Sysmon for Linux) — overhead**
- LAUREL's own benchmark (load generator spawning trivial processes, measured on an AWS t2.small): CPU of auditd + dispatcher + LAUREL combined is ≈2× a plain auditd setup with `log_format=ENRICHED`; Elastic auditbeat used ≈2.5× LAUREL's CPU time under the same load. **PROVEN** (project's own benchmark, small-VM class hardware) — [LAUREL performance.md](https://github.com/threathunters-io/laurel/blob/3c0ff97dbeaa56e71fd6eb4f400ba07e3547744c/performance.md)
- Same benchmark's CPU ranking, lowest first: auditd 2.8.5 RAW → go-audit → auditd ENRICHED → Sysmon for Linux 1.0.2 → LAUREL 0.1.6-pre → Auditbeat 7.16.0; Sysmon-for-Linux's number excludes its in-kernel eBPF cost, so it is understated. (2021-era versions.) — [LAUREL performance.md](https://github.com/threathunters-io/laurel/blob/3c0ff97dbeaa56e71fd6eb4f400ba07e3547744c/performance.md); [Sysmon for Linux perftest mirror](https://backiee.wasmer.app/http_github_com/tmaccs/SysmonForLinux/tree/main/perftest)
- go-audit fixes only one of auditd's log-format quirks and does not do all of auditd's ENRICHED translations. — [LAUREL performance.md](https://github.com/threathunters-io/laurel/blob/3c0ff97dbeaa56e71fd6eb4f400ba07e3547744c/performance.md)
- An academic paper reports auditd "incurs very high overheads for system-call granularity data collection, slowing down programs by 5× or more" — applies to capture-everything provenance collection, not to a trimmed exec/persistence ruleset. **PROVEN** for the heavy case — [NSF PAR paper 10554458](https://par.nsf.gov/servlets/purl/10554458)

**osquery (and Fleet)**
- osquery's watchdog defaults: worker killed above 200 MB RAM (100 MB in restrictive mode) or 25% CPU sustained for 9 s (18% restrictive); maintainers recommend cgroups for hard memory caps; the watchdog samples on an interval so brief overshoot is possible. **PROVEN** (design limits, i.e. a built-in upper bound on footprint) — [osquery community thread on limiting resources](https://chat.osquery.io/t/23010765/what-are-some-osquery-flags-that-folks-use-to-limit-osquery-); [Uptycs KB: limit endpoint resource utilization](https://support.uptycs.com/portal/en/kb/articles/how-to-limit-endpoint-resource-utilization)
- Official docs: process/socket auditing "may introduce additional CPU overhead and greatly increase the number of log events"; enabling BPF events turns on both `bpf_process_events` and `bpf_socket_events`; on busy hosts mask the audit journal socket. — [osquery docs: process and socket auditing](https://osquery.readthedocs.io/en/stable/deployment/process-auditing/)
- Evented tables that are subscribed but not queried keep buffering; community guidance is "don't enable them if unused; if used, query them more often than once a minute". One operator halved watchdog-limit violations by cutting the events query interval from 60 s to 10 s. On low-core VMs constrained by cgroups the worker can be killed while bursting to drain an event backlog. **PROVEN** (operational reports) — [osquery chat: evented tables](https://chat.osquery.io/t/2495/wave-hey-friends-if-disable-events-false-and-enable-bpf-even); [osquery PR #7329](https://github.com/osquery/osquery/pull/7329)

**Wazuh**
- Wazuh 5.x docs: manager minimum 4 GB RAM / 8 cores, recommended 8 GB / 16 cores; dashboard minimum 4 GB / 2 cores. 4.x docs: server minimum 2 GB / 2 cores, recommended 4 GB / 8 cores. All-in-one quickstart (1–25 agents): 8 GiB RAM, 4 vCPU. **PROVEN** (official) — [Wazuh 5.0-rc manager docs](https://documentation.wazuh.com/5.0-rc/installation-guide/wazuh-manager/index.html); [Wazuh current server docs](https://documentation.wazuh.com/current/installation-guide/wazuh-server); [Wazuh 5.0-rc dashboard docs](https://documentation.wazuh.com/5.0-rc/installation-guide/wazuh-dashboard/index.html)
- A user running the all-in-one on 8 GB / 4 vCPU / 38 GB disk lost dashboard events over time; responders attributed it to OpenSearch disk watermarks and JVM memory behaviour and said stable all-in-one needs significantly more headroom than documented minimums (forum opinion). — [Wazuh mailing list thread](https://groups.google.com/g/wazuh/c/afBxk9gpHZI)
- Agent alone: "35 MB of RAM on average" (old 4.1 docs figure). — [Wazuh 4.1 agent docs](https://documentation.wazuh.com/4.1/installation-guide/wazuh-agent)

**Network: Suricata / Zeek / CrowdSec / fail2ban**
- CrowdSec engine idles around 100 MB (blogger's boxes); a forum user measured 96.86 MiB and 0.4–1.5% CPU idle; on a 1 GB VPS a user reports it "hogs" the machine. **PROMISING** (anecdotal) — [LumaDock: Suricata vs CrowdSec](https://lumadock.com/tutorials/suricata-vs-crowdsec?language=spanish)
- Suricata: ~373 MB resident on a 4 GB box in one report; a Suricata 6.0.9 container with 60,000+ signatures sat at ~1.5 GB baseline and grew to ~2.5 GB under attack traffic; pfSense forum guidance is 4 GB available RAM for IDS/IPS packages and "be very cautious" with rule count at 2 GB. **PROVEN** as anecdotes, highly ruleset-dependent — [NethServer thread](https://community.nethserver.org/t/suricata-and-ntopng-memory-consumption/10757); [Suricata forum](https://forum.suricata.io/t/memory-increases-as-attack-traffic-keeps-being-played/3369/4); [Netgate forum](https://forum.netgate.com/post/716550)
- No concrete Zeek memory figures were found.

**Agentless (Sandfly-style)**
- Sandfly runs over SSH, pushes a self-contained userspace binary, loads no kernel modules and does not rely on eBPF; version 5.0 added agentless drift detection (compare host state to an expected baseline), arguing classic FIM misses fileless malware, new kernel modules and persistence changes. Claims to de-cloak eBPF/LKM-rootkit-hidden processes. Commercial product. Vendor claims; no independent test of what scan-interval-based agentless misses was found. **PROMISING** — [Risky Business catalog: Sandfly](https://risky.biz/catalog/sandfly-security/); [Sandfly 5.0 release post](https://sandflysecurity.com/blog/sandfly-5-0-agentless-drift-detection-new-ui-and-wider-linux-coverage)

**Evasion / blind spots (all sensors)**
- io_uring: ARMO's "Curing" PoC rootkit (April 2025) does C2 and file/network operations purely through io_uring, with no syscalls for hook-based sensors to see. Falco was "entirely blind" even with custom rules; Tetragon did not flag it in default configuration but can catch io_uring operations if the user writes Kprobe/LSM-hook policies (Isovalent's position: not a vulnerability, since Tetragon can hook almost anywhere); Microsoft Defender for Endpoint on Linux showed similar blind spots. Falco maintainers said they were working on a plugin for eBPF LSM hooks. Curing is free on GitHub for self-testing. **PROVEN** — [BleepingComputer, Apr 2025](https://bleepingcomputer.com/news/security/linux-io-uring-security-blindspot-allows-stealthy-rootkit-attacks); [ARMO blog](https://www.armosec.io/blog/io_uring-rootkit-bypasses-linux-security); [The Hacker News, Apr 2025](https://thehackernews.com/2025/04/linux-iouring-poc-rootkit-bypasses.html?m=1); [CSO Online](https://www.csoonline.com/article/3971170/proof-of-concept-bypass-shows-weakness-in-linux-security-tools-claims-israeli-vendor.html); [InfoQ, Sep 2025](https://www.infoq.com/news/2025/09/linux-security-rootkit)
- TOCTOU on syscall arguments: DEF CON talk "Trace me if you can: Bypassing Linux Syscall Tracing" (Rex Guo, Junyuan Zeng) shows TOCTOU flaws in syscall tracing that let an attacker swap arguments after the sensor reads them; reliable even with seccomp/SELinux/AppArmor enforced; includes a Falco bypass demo. **PROVEN** — [DEF CON forum entry](https://forum.defcon.org/node/241839)
- Sensor silencing by a same-privilege process: a 2026 write-up claims Falco, Tracee v0.24.1 and Tetragon v1.4.0 can each be silenced by editing their BPF maps with one `bpftool` command while the tool still looks healthy; requires CAP_BPF/root. Single-source, no vendor response or CVE found. **PROMISING** — [dev.to: "I silenced Falco, Tracee, and Tetragon with a single bpftool command"](https://dev.to/azqzazq1/i-silenced-falco-tracee-and-tetragon-with-a-single-bpftool-command-1i46)
- Kernel-rootkit blinding of eBPF tools is documented by THC ("Breaking eBPF Security: How Kernel Rootkits Blind Observability Tools"); the LinkPro rootkit (reported Oct 2025, AWS-hosted Kubernetes) hooks the `bpf` syscall to hide its own programs from `bpftool`. **PROVEN** (in-the-wild + PoC) — [THC](https://iq.thc.org/breaking-ebpf-security-how-kernel-rootkits-blind-observability-tools); [Andrea Fortuna, May 2026](https://andreafortuna.org/2026/05/27/ebpf-rootkits/)

**Project health signals**
- Tracee: releases visible up to v0.23.0 in search results and v0.24.1 referenced by a 2026 researcher; current maintenance cadence not confirmed. — [Tracee v0.23.0 release](https://newreleases.io/project/github/aquasecurity/tracee/release/v0.23.0); [dev.to bpftool post](https://dev.to/azqzazq1/i-silenced-falco-tracee-and-tetragon-with-a-single-bpftool-command-1i46)
- Supply-chain risk of the security tooling itself: in March 2026 attackers used stolen credentials (a service-account PAT without MFA) to publish malicious Trivy binaries, container images and GitHub Action tags from Aqua's GitHub organisation (CVE-2026-33634). Aqua also maintains Tracee. **PROVEN** — [Barracuda advisory](https://trust.barracuda.com/security/information/trivy-supply-chain-compromise); [AhnLab advisory](https://asec.ahnlab.com/en/93110/)

### Inferences
- **Opinionated stack for 2–4 vCPU / 4–8 GB shared with apps** (my recommendation, built on the above):
  1. **One exec/file/network event stream, not three.** Choose ONE of: (a) Falco with the modern eBPF driver — best out-of-the-box rule content, detection-only; (b) auditd + a trimmed Neo23x0 ruleset + LAUREL for JSON — zero extra kernel components, in every distro, cost ≈2× plain auditd CPU; (c) Tetragon — lowest-level hooks incl. LSM (the only one of the three that can be configured to see io_uring), but you must author TracingPolicies yourself. For a solo operator who wants content rather than a toolkit: Falco, or auditd+LAUREL if RAM is the binding constraint.
  2. **osquery as the state/inventory engine** (scheduled snapshot queries → diff). Its watchdog gives a hard ceiling (≤200 MB, ≤25% CPU bursts) which is what a shared VM needs. Run it standalone (config file + local results log); skip Fleet for one VM **[background: Fleet needs MySQL + Redis]**.
  3. **journald + a single shipper (Vector or Fluent Bit) → off-box**; local store SQLite/DuckDB files rather than Loki/ClickHouse.
  4. **CrowdSec or fail2ban only if SSH/HTTP must be internet-exposed**; if SSH is moved behind WireGuard/Tailscale-style access, brute-force noise disappears and neither is needed.
  5. **Canary tokens + egress default-deny with logging** (see §5) — zero resource cost, highest signal.
- **Cut for a solo operator:** Wazuh manager/indexer/dashboard (documented minimums alone equal the whole VM); Suricata/Zeek (hundreds of MB to GBs, and on a single host you already see process↔socket attribution from the host sensor); Tracee/Kunai/Sysmon-for-Linux if Falco or auditd is already present; Velociraptor server (use only as an ad-hoc offline collector); AIDE/Tripwire if osquery file hashing + package-manager verification is in place.
- **Redundant pairs:** Falco ↔ Tetragon ↔ Tracee ↔ Kunai ↔ Sysmon-for-Linux ↔ auditd exec rules (one process-event source is enough); AIDE ↔ Tripwire ↔ Wazuh syscheck ↔ osquery `file_events`/hash snapshots; fail2ban ↔ CrowdSec; Suricata ↔ Zeek; Loki ↔ ClickHouse; Wazuh agent ↔ (auditd + AIDE + rootcheck).
- **Hardening that removes blind spots cheaper than detecting them [background, verify]:** `kernel.io_uring_disabled=2` if no app needs io_uring (kernel ≥6.6), `kernel.unprivileged_bpf_disabled=1`, module loading locked after boot (`kernel.modules_disabled=1` or lockdown), auditd rules made immutable (`-e 2`). These convert the Curing / bpftool-map / LKM classes from "must detect" into "must first reboot or break a control", which is itself a loud drift event.
- Any on-box sensor is defeated by root (map tampering, `bpf`-syscall hooking, LKM). Therefore a root-level compromise must be assumed to blind the box; detection of that case has to come from off-box evidence (heartbeat gaps, off-box log stream stopping, external port/behaviour probes, canaries). 
- Published "X% overhead" numbers for eBPF sensors should all be labelled PROMISING at best; the only measured-on-small-VM data point found is LAUREL's t2.small benchmark.

## 2. Minimal high-value stack; what is redundant; what to cut

### Takeaway
For a low-change personal VM the highest-value, lowest-cost stack is: deterministic state inventory + diff (osquery or plain scripts), one process-event stream (Falco or auditd+LAUREL), canary tokens, egress deny-logging, and off-box log shipping — everything else (SIEM manager, NIDS, a second eBPF sensor, FIM daemon) is redundant or too heavy.

### Cited Findings
- Detection engineering, not telemetry volume, is the bottleneck even in enterprises: CardinalOps' 2025 report (fifth annual, June 2025) found production SIEMs detect only 21% of ATT&CK techniques although they ingest enough telemetry to cover over 90%, and ~13% of rules are functionally broken (the 13% figure appeared in a press summary I could not pin to one outlet — verify in the report). — [Help Net Security, 2025-06-09](https://www.helpnetsecurity.com/2025/06/09/siem-detection-coverage/); [BetaNews, 2025-06-05](https://betanews.com/2025/06/05/enterprise-siems-are-detecting-only-21-percent-of-threat-techniques)
- Wazuh's documented minimums (manager 4 GB/8 cores in 5.x; all-in-one 8 GiB/4 vCPU) match or exceed the entire target VM. — [Wazuh 5.0-rc manager docs](https://documentation.wazuh.com/5.0-rc/installation-guide/wazuh-manager/index.html)
- osquery's footprint is bounded by design (200 MB / 25% CPU watchdog). — [osquery community thread](https://chat.osquery.io/t/23010765/what-are-some-osquery-flags-that-folks-use-to-limit-osquery-)
- Auditd + LAUREL costs ≈2× plain auditd CPU; auditbeat ≈2.5× LAUREL. — [LAUREL performance.md](https://github.com/threathunters-io/laurel/blob/3c0ff97dbeaa56e71fd6eb4f400ba07e3547744c/performance.md)
- A practitioner purple-team lab uses Atomic Red Team for day-to-day validation "because it maps cleanly one-atomic-to-one-detection" and keeps Caldera as an optional layer — a signal of what a solo operator can actually sustain. — [Purple-Team Lab (Z. Boggan)](https://zionboggan-code.pages.dev/purple-team-lab/)

### Inferences
- Budget sketch (to be measured, not cited): Falco or auditd+LAUREL (tens to low hundreds of MB), osquery (≤200 MB hard cap), shipper (tens of MB), CrowdSec (~100 MB, optional). Target total: well under 0.5 vCPU average and under ~500 MB RAM; if it exceeds that, cut the eBPF sensor before cutting osquery.
- Because the 2025 CardinalOps and Picus data show that most failures are broken/untuned rules and logging gaps rather than missing sensors, a solo operator gets more from 30 verified checks than from 3,000 unverified vendor rules.
- The LLM should sit on the *diff and alert* outputs of this stack, not on raw event streams (see §6).

### Gaps
- No published study compares "minimal stack" vs "full stack" detection outcomes on single hosts.

## 3. Persistence detection: locations, tooling, and converting it to a deterministic baseline diff

### Takeaway
Elastic Security Labs' five-part "Linux Detection Engineering" persistence series (Aug 2024–Feb 2025) plus its MIT-licensed PANIX tool is the best public catalogue-and-test-harness pair; the right design is to enumerate every persistence location into a signed inventory and alert on any diff, with PANIX (which ships revert scripts) used to prove each location is actually covered. Real honeypot captures show the most common persistence on internet-facing Linux is still an injected `authorized_keys` entry (sometimes made immutable with `chattr`), installed within seconds.

### Cited Findings
- Elastic's series (author Ruben Groenewoud): part 1 "primer" covers cron, at and other common methods; part 2 "sequel" covers System V init, Upstart and more; a later part covers "creative and complex" mechanisms; part 4 "Approaching the Summit" includes PAM (malicious PAM modules); part 5 "The Grand Finale on Linux Persistence" (dated 2025-02-27) covers GRUB bootloader persistence (T1542 Pre-OS Boot) among others. Each technique is paired with detection rules and hunting queries (search summary; pages not fetched). **PROVEN** (primary vendor research) — [Primer](https://www.elastic.co/security-labs/primer-on-persistence-mechanisms); [Sequel](https://www.elastic.co/security-labs/sequel-on-persistence-mechanisms); [Approaching the summit](https://www.elastic.co/security-labs/approaching-the-summit-on-persistence); [Grand finale](https://www.elastic.co/security-labs/the-grand-finale-on-linux-persistence); [Malpedia dating of finale](https://malpedia.caad.fkie.fraunhofer.de/library/02b185d4-56b6-43eb-a106-be1bde03f2e7/)
- Elastic states its SIEM ships "over 1,000 prebuilt rules and more than 200 specifically dedicated to Linux". — [Elastic primer](https://www.elastic.co/security-labs/primer-on-persistence-mechanisms)
- PANIX: "highly customizable Linux persistence tool for security research, detection engineering, penetration testing, CTFs"; shell, MIT-licensed; "prioritizes functionality over stealth and is easily detectable"; each technique has a revert module; latest release seen v2.1.0 (adds five techniques incl. D-Bus persistence; v2.0.0 added sedexp-style udev persistence); techniques confirmed across the README summaries and Elastic articles: cron, SysV init scripts, rc.local, dynamic MOTD, udev rules, package-manager hooks, Git hooks, D-Bus, PAM and GRUB (`setup_grub.sh`); LD_PRELOAD and systemd-generator modules were NOT confirmed in what I could retrieve — check the README. — [PANIX on GitHub](https://github.com/Aegrah/PANIX); [PANIX project index](https://awesome.ecosyste.ms/projects/github.com%2FAegrah%2FPANIX); [Cyber Security News summary](https://cybersecuritynews.com/how-threat-actors-establish-persistence-on-linux-systems/amp/)
- Example PANIX invocation from the series: `sudo ./panix.sh --cron --default --ip 192.168.1.1 --port 2001`; the SysV module creates `/etc/init.d/ssh-procps`. — [Elastic sequel](https://www.elastic.co/security-labs/sequel-on-persistence-mechanisms)
- Same author also publishes ALPHA (companion repo). — [Aegrah/ALPHA](https://github.com/Aegrah/ALPHA)
- Honeypot evidence, April 2025 Cowrie capture: attacker wrote an SSH key into `authorized_keys` and set it append-only + immutable with `chattr`; "the most significant persistence mechanism was the installation of an SSH key". — [SANS ISC guest diary 32024](https://isc.sans.edu/diary/32024)
- Honeypot evidence, May 2026 case: backdoor key injected within 22 seconds of login, password changed, `.ssh` removed and recreated first (evicting existing keys); 93 IPs from the "mdrfckr" campaign list still hitting the sensor weeks later. — [SANS ISC diary 33220](https://isc.sans.edu/diary/33220)
- Sandfly's argument for drift detection over classic FIM: FIM often misses fileless malware, new kernel modules and persistence changes. (Vendor.) — [Sandfly 5.0](https://sandflysecurity.com/blog/sandfly-5-0-agentless-drift-detection-new-ui-and-wider-linux-coverage)
- General overview of Linux persistence mechanisms and how to find them (Oct 2024). — [Security Boulevard](https://securityboulevard.com/2024/10/linux-persistence-mechanisms-and-how-to-find-them)

### Inferences
- **Persistence inventory checklist [background — compiled from my prior knowledge of the Elastic series, MITRE ATT&CK Linux techniques and common hunting practice; paths not re-verified this session].** Each line = one deterministic collector whose normalised output is hashed and diffed:
  - Scheduled: `/etc/crontab`, `/etc/cron.{d,hourly,daily,weekly,monthly}/*`, `/var/spool/cron/**`, anacron; `at` spool (`/var/spool/at*`, `atq`); systemd timers (system + every user). (T1053)
  - systemd: unit files in `/etc/systemd/system`, `/run/systemd/system`, `/usr/lib/systemd/system`, `~/.config/systemd/user`; drop-ins (`*.d/*.conf`); generators (`/etc/systemd/system-generators`, `/usr/lib/systemd/system-generators`, user generators); enabled-state list; `ExecStart*` lines. (T1543.002)
  - Legacy init: `/etc/rc.local`, `/etc/init.d/*`, `/etc/rc*.d`, Upstart `/etc/init/*`. (T1037)

- **Turn it into a deterministic check:** (1) collectors emit canonical JSON (sorted, timestamps stripped); (2) each run is hashed and the manifest signed/shipped off-box; (3) diff engine classifies each change as *expected* (matches a change record the operator or the config-management run created within a time window) or *unexpected*; (4) only unexpected diffs go to the LLM, which explains and proposes, but the "is there a diff" decision is code, not model. This directly addresses the cited weakness that agents miss persistence: the LLM is never asked to *notice*, only to *interpret*.
- **Coverage proof:** run each PANIX module in a disposable clone of the VM, assert the diff engine reports it, then run the PANIX revert module and assert the diff clears. Any PANIX technique that yields no diff is a collector gap. PANIX is noisy by design, so passing PANIX proves location coverage, not stealth coverage.
- **Blind spots of a userland diff:** anything a rootkit hides from userland (hooked `getdents`, `bpf` syscall hooking as in LinkPro), in-memory-only implants, and persistence living outside the VM (cloud-init/user-data, provider snapshots, DNS, CI/CD deploy keys, the operator's laptop). Mitigate with an out-of-band view: provider API inventory, offline disk snapshot scan from another machine, and periodic rebuild.

## 4. Baseline/drift vs signature alerting; immutable/declarative OS

### Takeaway
I found no controlled study showing allowlisting/drift detection beats signature alerting on small stable hosts — the case is structural (PROMISING, not PROVEN): signatures demonstrably miss most attack actions (§5), while a low-change VM makes "anything new" a cheap, high-precision signal. Immutable/image-based systems make drift detection much simpler and make persistence harder, but they are not a silver bullet: Google has documented that a root attacker can swap a dm-verity device for a writable one at runtime, and data/state partitions and the deploy pipeline remain persistence surfaces.

### Cited Findings
- Google security advisory GHSA-6vq3-w69p-w63m: an attacker with a root shell can replace a dm-verity device with a plain linear device, leaving a "trusted" read-only root that is in fact modifiable for the rest of that boot; barrier to entry is high; marking the verity target immutable blocks replacement (kernel mitigation), though read-only-mode reloads can still succeed. So dm-verity protects against offline/disk tampering more reliably than against a live root compromise. **PROVEN** — [google/security-research GHSA-6vq3-w69p-w63m](https://github.com/google/security-research/security/advisories/GHSA-6vq3-w69p-w63m)
- bootc images are ostree filesystems; updating means building a new base image and switching to it; composefs is listed as the filesystem-integrity mechanism in that stack (dm-verity being the alternative used by other image-based systems). — [MiniDebConf Hamburg 2026 slides: immutable images](https://hamburg2026.mini.debconf.org/media/pages_files/slides-immutable-images.pdf)
- NixOS: the Nix store is writable only via the Nix daemon, but commenters note NixOS is not fully immutable (the rest of the system can change; a root attacker can redirect the symlinks); a NixOS forum thread discusses adding boot-time integrity checks for the store — i.e. it is not there by default. — [NixOS discourse: boot-time integrity checks for the Nix store](https://discourse.nixosstag.fcio.net/t/boot-time-integrity-checks-for-the-nix-store/36793); [Lemmy discussion](https://lemm.ee/comment/1939408)
- Overlay filesystems let changes persist over a read-only base, weakening "immutable" claims. — [Ubuntu discourse: The Immutable Linux Paradox](https://discourse.ubuntu.com/t/the-immutable-linux-paradox/66456)
- Design pattern for a fully verified image: dm-verity root with root hash supplied via verified boot parameters, reboot-on-corruption mode, user data on a separate LUKS partition "so the system itself has no persistence path" (a proposal, not a product). — [Qubes forum thread](https://forum.qubes-os.org/t/building-a-fully-immutable-linux-os-image-fully-verified-with-your-own-secure-boot-key/34412)
- Commercial drift detection for mutable hosts exists (Sandfly 5.0: compare observed host state with expected baseline, agentless). — [Sandfly 5.0](https://sandflysecurity.com/blog/sandfly-5-0-agentless-drift-detection-new-ui-and-wider-linux-coverage)
- Enterprises with far more resources still alert on only 14% of simulated attacks (Picus 2025) and cover 21% of techniques (CardinalOps 2025) with signature/rule approaches. — [Picus press release via SecurityInfoWatch](https://www.securityinfowatch.com/cybersecurity/press-release/55309275/picus-security-picus-security-report-flags-weakening-cyber-defenses); [Help Net Security](https://www.helpnetsecurity.com/2025/06/09/siem-detection-coverage/)

### Inferences
- **Is "immutable and rebuildable" fundamentally better than "watch a mutable VM"?** For the OS layer, yes in three ways: (1) the baseline *is* the image/flake — no separate inventory to maintain; (2) drift detection collapses to "does running state equal the declared image digest + a short list of writable paths"; (3) response becomes "rebuild", which also evicts unknown persistence. But it only shrinks the problem: writable state (`/var`, `/etc` overlays, home dirs, container volumes, databases, web-app upload dirs), in-memory implants, credentials, and the build/deploy pipeline remain. Monitoring is still needed for runtime behaviour, credential theft and data exfiltration, which immutability does not touch.
- Pragmatic middle path for a solo operator who will not migrate distro: declarative config (Ansible/cloud-init/Nix-on-any-distro) in git + read-only mounts where possible (`/usr` ro, `noexec` on `/tmp`, `/var/tmp`, `/dev/shm`, upload dirs) + scheduled rebuild from scratch (e.g. monthly) + the §3 diff. A rebuild cadence bounds attacker dwell time even when detection fails.
- Baseline diff has two honest failure modes: (a) change fatigue — every `apt upgrade` produces hundreds of diffs unless package-owned files are verified through the package manager and excluded; (b) "living in the baseline" — an attacker who was present when the baseline was taken, or who persists only in data the baseline excludes. Hence the baseline must be taken from a fresh build, not from the running VM.
- Label: "drift/allowlisting outperforms signatures on small stable hosts" = **PROMISING** (strong structural argument, vendor support, no measured comparison found). "Immutable OS makes persistence impossible" = **HYPE** (contradicted by the Google advisory and by state/overlay paths).

### Gaps
- No empirical study comparing drift/allowlist detection with signature alerting on single hosts was found.
- No source directly compares drift tooling across bootc, NixOS, Fedora CoreOS, Talos under a persistence threat model.
- IMA/EVM and fs-verity overhead and usability on a general-purpose VM: no sources retrieved.

## 5. "Only ~30–40% of attack actions trigger alerts": the sources, and how to catch silent attacks

### Takeaway
The exact "30–40%" figure was not found in any primary source; the published numbers are *worse*: Picus Blue Report 2025 — 54% of simulated attacks logged, only 14% alerted; Mandiant Security Effectiveness Report 2020 — 26% detected, 9% alerted, 53% missed entirely; CardinalOps 2025 — rules exist for 21% of ATT&CK techniques. The defensible response is to stop depending on behaviour signatures: add tripwires that only an intruder touches (honeytokens), deny-by-default egress with logging, deterministic drift checks, and scheduled hunts.

### Cited Findings
- Picus Blue Report 2025 (published Aug 2025; >160 million attack simulations by Picus customers, Jan–Jun 2025): logging coverage 54% (flat year on year); only 14% of attacks generated alerts; prevention effectiveness fell from 69% (2024) to 62% (2025); only 3% of data-theft attempts were blocked; press headline "46% of enterprise passwords vulnerable to cracking"; one summary adds that 50% of detection-rule failures stemmed from logging issues (outlet not pinned down in my search — verify in the report itself). **PROVEN** (large vendor dataset, enterprise environments; 54%/14% figures consistent across outlets) — [Picus press release via SecurityInfoWatch](https://www.securityinfowatch.com/cybersecurity/press-release/55309275/picus-security-picus-security-report-flags-weakening-cyber-defenses); [Security Today, 2025-08-18](https://securitytoday.com/articles/2025/08/18/46-of-enterprise-passwords-vulnerable-to-cracking.aspx); [Picus webinar page](https://www.picussecurity.com/resource/webinar/blue-report-2025-how-to-act-on-160m-attack-simulation-findings)
- Mandiant Security Effectiveness Report 2020 (May 2020; tests in production environments across 11 industries against 123 security technologies): 53% of attacks infiltrated without detection; 26% detected; 33% prevented; alerts generated for only 9%; only 4% of reconnaissance activity generated an alert. **PROVEN** (older) — [Report PDF](https://services.google.com/fh/files/misc/security_effectiveness_report_2020.pdf); [Business Wire](https://www.businesswire.com/news/home/20200505005192/en/Mandiant-Security-Effectiveness-Report-2020)
- CardinalOps 2025 (June 2025): enterprise SIEMs have detections for 21% of ATT&CK techniques (up 2 points), miss 79%; SIEMs ingest on average 259 log types and ~24,000 log sources — enough to cover >90% of techniques; ~13% of rules are broken. One outlet (SecureWorld) reports "36% of relevant techniques" — unreconciled with the 21% figure. — [Help Net Security](https://www.helpnetsecurity.com/2025/06/09/siem-detection-coverage/); [BetaNews](https://betanews.com/2025/06/05/enterprise-siems-are-detecting-only-21-percent-of-threat-techniques); conflicting: [SecureWorld](https://www.secureworld.io/industry-news/siem-sprawl-makes-detection-tough)
- Honeytokens — evidence is qualitative: Thinkst's CEO: "If the aim is to increase the time taken for attackers, canary tokens work well"; a penetration tester reports canary tokens made them hesitant to use found credentials (deterrence effect). — [Dark Reading: credential canaries](https://www.darkreading.com/cyberattacks-data-breaches/credential-canaries-create-minefield-for-attackers)
- Honeytoken limits: static tokens can be recognised/avoided by skilled attackers and are not refreshed (competing vendor's view); attackers themselves know the technique — Cisco Talos reported MuddyWater malware using canary tokens to detect analysis. — [Acalvio](https://www.acalvio.com/?p=1920); [TSARKA Science paper (2026), qualitative synthesis incl. Grafana Labs 2025 incident](https://science.cert.kz/journal/index.php/ojs/article/view/23)
- Real post-compromise behaviour on SSH honeypots is fast and automated (key injection within 22 s; password change; `.ssh` wipe) — meaning behavioural detection has seconds, and the persistent artefact (the key) is the reliable thing to detect. — [SANS ISC diary 33220](https://isc.sans.edu/diary/33220); [SANS ISC diary 32024](https://isc.sans.edu/diary/32024)
- Only 3% of data-theft attempts blocked in Picus 2025 → egress is the least-defended stage in practice. — [Picus press release via SecurityInfoWatch](https://www.securityinfowatch.com/cybersecurity/press-release/55309275/picus-security-picus-security-report-flags-weakening-cyber-defenses)

### Inferences
- The user's "~30–40%" figure is probably a paraphrase or comes from a different study (possibly an LLM-agent benchmark); the report should cite Picus 2025 (54% logged / 14% alerted) and Mandiant 2020 (26% detected / 9% alerted) instead and state the gap: roughly 40 points between "evidence existed in logs" and "anyone was told". That gap is exactly where an LLM hunting over logs could add value — and where deterministic diff checks add value more cheaply.
- **Silent-attack controls ranked by value/cost for one VM:**
  1. *Honeytokens* (PROMISING: strong logic, near-zero false positives by construction, weak published measurement): fake AWS key in `~/.aws/credentials` and in a decoy `.env`; a decoy SSH private key whose public half is authorised nowhere real but watched; a canary DNS name embedded in a decoy config; a decoy DB row/user; `auditd`/Falco watch on *reads* of decoy files. Triggers arrive out-of-band (the token provider), so they survive on-box sensor blinding.
  2. *Egress default-deny + log drops* (nftables/provider firewall): a personal VM talks to a short, knowable list of destinations (package mirrors, ACME, git remote, backup target, LLM API). Any dropped outbound packet is a high-precision alert covering C2, miners, exfil and reverse shells regardless of technique.
  3. *Deterministic drift check* (§3) on a timer, signed and shipped off-box.
  4. *Scheduled hunts* (hourly/daily queries, not alerts): processes whose binary is deleted or lives in `/tmp`,`/dev/shm`; processes with no package owner; new listening sockets; interactive shells spawned by web/DB service users; logins from a new ASN/country; outbound connections by rarely-networked binaries; high CPU by unknown process (miner).
  5. *Honeypot service* (Cowrie on port 22 with real SSH moved/behind VPN; OpenCanary) — lower value for a single VM: it mostly measures background internet noise; its best use is as a tripwire on *internal/loopback/tailnet-only* ports where no legitimate client ever connects.
  6. *Anomaly baselines* (login-time, process-set, destination-set) — easy on a stable VM because the "normal" set is tiny; implement as set-difference, not ML.
- Heartbeat inversion: the off-box side should alert when the VM's signed heartbeat/diff *stops*, since a root attacker's first move may be to kill sensors.

### Gaps
- No primary source for the exact "30–40% of attack actions trigger alerts" claim. MITRE ATT&CK Evaluations data was not searched/retrieved.
- No controlled measurement of honeytoken detection rate or time-to-detect (Thinkst or independent) was found; evidence is anecdotal and vendor-supplied.
- No aggregate 2025–2026 honeypot statistics (share of sessions that install miners vs keys vs botnet clients) were found — only case studies.
- No source found quantifying egress-allowlist effectiveness.

## 6. LLM over sensors: architectures, measurements, prompt injection via logs, token cost

### Takeaway
Measured results for LLM alert triage exist but are thin and mostly about false-positive reduction, with false-negative rates rarely reported (PROMISING); meanwhile injection through attacker-controlled log fields is now measured and serious — 2026 papers report ~83% average attack success undefended and persona-hijack payloads suppressing 68% of malicious logs under a naive classifier, with layered defences still leaving ~8% residual success (PROVEN as a risk). The LLM must therefore be an explainer/prioritiser over pre-filtered, typed events and never the sole gate or a path from log text to tool calls.

### Cited Findings
- CORTEX (multi-agent alert triage; arXiv 2510.00311, submitted 30 Sep 2025; listed at NeurIPS 2025): false-positive rate 14.2% vs 24.9% for a single-agent tool-use baseline and 29.8% for prompt-only; design escalates if *any* investigative workflow marks the alert actionable (bias against false negatives); no false-negative rate surfaced in my search; a secondary blog reports actionable-decision F1 rising from 0.66 to 0.78 (unverified against the paper). **PROMISING** — [CORTEX, arXiv](https://arxiv.org/html/2510.00311v1); [NeurIPS listing](https://neurips.cc/virtual/2025/137134)
- AACT (Turcotte et al., arXiv 2505.09843): a secondary blog reports a deployed six-month result of a 61% cut in analyst-facing alerts with a 1.36% false-negative rate — NOT confirmed from the primary paper. **PROMISING / unverified** — [Security Scientist blog](https://www.securityscientist.net/blog/soc-triage-automation/)
- "Before You Hand Over the Wheel: Evaluating LLMs for Security Incident Analysis" (arXiv 2603.06422, Mar 2026): alert-triage accuracy GPT-5 98% / 97.1%, Claude-4.5-Sonnet 96% / 88.57% on two small sets (100 alerts from TII-SRC-23; 35 from CIC-IDS2017 with only 5 true positives) — too small to trust for false negatives. **PROMISING** — [arXiv 2603.06422](https://arxiv.org/pdf/2603.06422)
- "Poisoning the Watchtower" (Pandey & Bhujang, arXiv 2605.24421, May 2026): defines "log-substrate prompt injection" (malicious text inside the log evidence the LLM analyses); four-class taxonomy — S1 direct override, S2 persona hijack, S3 context manipulation, S4 obfuscated payloads; persona hijacks suppress 68% of malicious logs under a naive classifier and remain effective under stronger defences (search summary). **PROVEN** (measured) — [alphaXiv 2605.24421](https://www.alphaxiv.org/abs/2605.24421)
- LogInject — "Context Contamination in LLM Analysis of Network Security Logs" (Karanjai et al., arXiv 2607.14493, July 2026): "passive prompt injection" — payloads in log-generating fields persist in storage and fire when an analyst later queries the LLM; benchmark of 12,847 log entries incl. 2,569 adversarial; three production LLMs; four objectives (activity concealment, false-positive generation, information exfiltration, output hijacking); defences evaluated: prompt-level (spotlighting, instruction hierarchies), data-level (canary injection, input sanitisation), architectural (dual-LLM validation); layered defences give 90.4% attack reduction but 8.4% residual vulnerability. Secondary summaries add: 83.4% average undefended attack success across the three models; on GPT-4o 87.3% → 8.4% with layered defences; spotlighting alone roughly halves success; strict filters cause false positives on benign entries containing command-line examples. **PROVEN** (abstract figures) / secondary figures unverified — [arXiv 2607.14493](https://arxiv.org/abs/2607.14493); [NeuralTrust blog, updated Oct 2026](https://neuraltrust.ai/blog/ai-soc-prompt-injection)
- Practitioner demonstration of indirect prompt injection into SOC/SIEM AI agents via log files (user-agent strings, usernames, etc.). — [LevelBlue SpiderLabs: Rogue AI agents in your SOCs and SIEMs](https://www.levelblue.com/blogs/spiderlabs-blog/rogue-ai-agents-in-your-socs-and-siems-indirect-prompt-injection-via-log-files)
- A widely repeated Aug 2025 Sygnia case (an XDR AI summary reading poisoned PowerShell logs and calling credential dumping "routine system maintenance") could only be confirmed via secondary blogs. **Unverified** — [NeuralTrust blog](https://neuraltrust.ai/blog/ai-soc-prompt-injection)
- Vendor agent design precedent: Google SecOps' purple-team agent connects through a remote MCP server and checks every outgoing request against a code-level allowlist (controls live in code, not the prompt). — [Google Cloud Community, Aug 2026](https://security.googlecloudcommunity.com/google-security-operations-2/how-we-built-an-agentic-purple-team-system-for-detection-validation-in-google-secops-8124)

### Inferences
- **Reference pipeline for one VM** (synthesis): sensors → normalise to a typed schema (OCSF or ECS field names; each attacker-influenceable field tagged `untrusted`) → deterministic rules + drift diff → dedupe/aggregate (group by rule × process lineage × time window; count instead of repeat) → enrich from trusted sources only (package ownership, baseline membership, first-seen time, ASN) → **deterministic severity floor** (canary hit, unexpected persistence diff, egress deny, new UID-0, sensor heartbeat loss page the human directly, bypassing the LLM) → LLM summarises/correlates/prioritises the remainder → human. The LLM may raise priority; it must not be able to *lower* anything below the deterministic floor or close an alert unattended.
- **Injection mitigations mapped to the 2026 papers:** (1) field typing + quoting/spotlighting — untrusted strings (usernames, user-agents, URLs, filenames, command lines, hostnames, container names/labels, commit messages, MOTD text) wrapped in delimiters with random nonces, length-capped, control characters and unusual Unicode stripped or escaped; (2) privilege separation — the model that reads raw log text has no tools; a second model/step that can call tools sees only structured verdict fields (enums, IDs, numbers), never free text (dual-LLM pattern); (3) tool calls parameterised only from typed fields validated by code (an IP must parse as an IP and be in the event; a path must match an allowlist regex); (4) read-only tools by default, anything state-changing behind human approval; (5) canary instructions in the prompt to detect hijack; (6) since ~8% residual attack success survives layered defences, design so that a fully hijacked LLM can at worst produce a wrong *summary*, not suppress a deterministic alert or execute a command.
- A log-borne injection is itself a detection: a regex/heuristic pre-filter flag ("log field contains instruction-like text addressed to an AI/analyst") should raise priority, not just be sanitised — with the paper's caveat that documentation and CLI examples will false-positive.
- **Token-cost reasoning (my arithmetic; assumptions explicit, prices deliberately not quoted — unverified):** a quiet VM can still emit 10^4–10^6 raw process/network events per day; at ~150–300 tokens per JSON event that is ~2M–300M input tokens/day — unaffordable and pointless. After rules + dedupe, a tuned single VM should yield on the order of 10–100 alert groups/day; at ~1–2k tokens each with enrichment that is ~10k–200k input tokens/day, i.e. trivially cheap on a small model, leaving budget for a daily "hunt digest" (aggregated counts, new-entity lists) of a few tens of thousands of tokens on a stronger model. Design rule: the LLM never reads raw streams; it reads diffs, aggregates and alert groups. Event-rate figures here are estimates — measure on the VM.
- False negatives are the under-measured risk in the triage literature (CORTEX reports FP rates; the one FN figure found is second-hand). For a solo operator the asymmetric choice is: let the LLM *reduce reading effort* (summaries, grouping), not *reduce alert count* on the high-severity classes.

### Gaps
- Could not read the three arXiv papers in full (host blocked); per-model/per-defence tables are not verified. The 83.4% and 87.3% figures are second-hand.
- No published measurement of LLM triage on single-host Linux telemetry (Falco/auditd/osquery) — all studies are SOC/enterprise alert datasets.
- No sourced numbers for event volumes per day of Falco/auditd/osquery on a small VM, and no sourced LLM price points included (deliberately).
- OCSF vs ECS for LLM consumption: no comparative evidence found.

## 7. Detection-as-code and purple teaming (incl. LLM-driven loops and hallucinated rules)

### Takeaway
Atomic Red Team (one atomic ↔ one detection) plus PANIX for persistence is the sustainable validation harness for one VM; LLM-driven purple loops (Caldera/Atomic → check alert → write rule → replay) exist in 2025–2026 as papers, conference talks and vendor previews, but published evidence measures mostly *syntactic validity/convertibility* of generated rules, not whether they fire — so every generated rule must pass a mechanical gate: lint, fire on replay, stay silent on a benign corpus.

### Cited Findings
- AUTOSIGMA (Ghaffarzadegan et al., arXiv 2608.19011, Aug 2026): turns CTI reports into Sigma rules using knowledge-base enrichment, matching against existing Sigma rules (template grounding) and an LLM-as-a-Judge loop; evaluation checks syntactic validity and whether rules convert to SIEM queries with sigma-cli; in an ablation on one TrendMicro report the OpenAI variant without the judge produced 21 valid rules of 24 (12.5% invalid), 100% with the judge loop (search summary; single-report data point). **PROMISING** — [arXiv 2608.19011](https://arxiv.org/pdf/2608.19011)
- LLMCloudHunter (arXiv 2407.05194, 2024): 99.18% of generated rule candidates compiled and converted into Splunk queries — a conversion-success metric, not a detection-efficacy metric. — [arXiv 2407.05194](https://arxiv.org/pdf/2407.05194)
- "From Texts to Rules: Generating Sigma Rules with Large Language Models from Cyber Threat Reports" accepted at USENIX Security 2026 (Cai et al.). — [USENIX Security '26](https://www.usenix.org/conference/usenixsecurity26/presentation/cai)
- BAGLEY (SBSeg 2026, Portuguese): LLM-orchestrated purple-team cycles integrating MITRE Caldera emulation with Wazuh SIEM analysis in a continuous "cognitive loop". — [SBC OpenLib](https://sol.sbc.org.br/index.php/sbseg/article/view/44293)
- BSides Luxembourg 2026 talk: n8n + Elastic + Caldera + LLM pipeline; if a technique goes undetected the system checks SIEM logs and, if the activity was logged, suggests a Sigma use case. — [BSides Luxembourg 2026](https://pretalx.com/bsidesluxembourg-2026/talk/JRZGUH/)

### Inferences
- **The "hallucinated rule that looks right and matches nothing" risk is real but under-measured**: the literature found reports validity/conversion (87.5%→100% valid in AUTOSIGMA's ablation; 99.18% convertible in LLMCloudHunter), which says nothing about whether the rule matches real telemetry (wrong field names for the local log source, wrong logsource category, over-specific command-line strings). The Google agent's "how far did the evidence travel" framing is the right metric. Label "LLM writes your detections" = **PROMISING with a mandatory verification gate**; "autonomous self-healing detection" = **HYPE** on current evidence.
- **Rule acceptance gate (make it CI, not judgement):**
  1. *Lint/compile*: `sigma check` + pySigma conversion to the local backend; `falco --validate`/dry-run for Falco rules; YARA compile. Reject unknown fields against the actual schema of the local log source.
  2. *True-positive test*: run the specific atomic/PANIX module in a disposable clone → the rule must fire, with the expected rule ID and ATT&CK tag, within N seconds. Record the raw events as a fixture.
  3. *True-negative test*: replay a benign corpus (≥1–2 weeks of the VM's own recorded normal telemetry incl. `apt upgrade`, deploys, backups, cron, logins) → zero or under-budget hits.
  4. *Variation test*: 2–3 mutated variants of the technique (different path, interpreter, encoding) to catch string-overfitting; have a different model (or a human) write the variants so the author does not grade its own work.
  5. *Regression*: fixtures kept in git; every rule/sensor/OS upgrade re-runs the whole suite (catches the 13%-broken-rule drift); nightly "canary atomic" in production-like clone proves the pipeline end to end (sensor → shipper → store → alert → notification).
  6. *Telemetry-gap triage*: if the atomic ran and no raw event exists, it is a sensor/visibility gap — do not let the LLM "fix" it with a rule.
- **Running the loop safely:** execute techniques only in a snapshot/clone with no real secrets, no production network path and blocked egress; the executor identity is separate from the monitoring agent; technique allowlist (no destructive/impact atomics, no real exfil targets); mandatory cleanup verified by the §3 drift check returning to baseline (a purple run that leaves residue is itself a finding); tag test activity with a marker so alerts are attributable but do not auto-suppress on the marker (attackers could spoof it); never hand the LLM both "run arbitrary attack" and "edit detection rules" on the production VM in one loop — rule changes land by PR.
- Tool fit for one VM: Atomic Red Team + PANIX + Curing = sufficient. Caldera is heavier (server + agent, designed for multi-host operations); Stratus Red Team is cloud-control-plane-focused (useful only if the VM's cloud account is in scope); Splunk Attack Range / VECTR / DeTT&CT are enterprise programme tooling — overkill; a spreadsheet or YAML matrix of technique → test → rule → last-pass date gives the same value. **[background, tool descriptions not re-verified this session]**

## 8. ATT&CK / D3FEND mapping and which techniques matter for an internet-facing personal VM

### Takeaway
Current frontline data says the VM will most likely be compromised through an exploited internet-facing service or weak/stolen credentials, by automated actors who persist within seconds; so a realistic target is not "% of the Linux matrix" but verified coverage of a short list — exposed-service exploitation, valid accounts/SSH, account and key manipulation, scheduled-task/systemd persistence, ingress tool transfer, miners, defence evasion against the sensors, and exfil/C2 egress.

### Cited Findings
- M-Trends 2026 (Mandiant/Google, covering 2025 investigations; published ~April 2026): exploits were the top initial infection vector for the sixth straight year at 32%; voice phishing 11%; prior compromise 10%; global median dwell time rose to 14 days (from 11); 122 days median for espionage / DPRK IT-worker cases; SecurityWeek headline: initial-access handoff shrank "from hours to 22 seconds"; 146 of the new malware families tracked in 2025 targeted Linux (55 macOS). **PROVEN** — [Google Cloud blog: M-Trends 2026](https://cloud.google.com/blog/topics/threat-intelligence/m-trends-2026); [SecurityWeek](https://www.securityweek.com/m-trends-2026-initial-access-handoff-shrinks-from-hours-to-22-seconds/)
- Red Canary 2026 Threat Detection Report: identity threats up 850% in 2025 and 53% of detection volume (20% in 2024); T1078.004 Cloud Accounts highlighted; no Linux-specific ranking surfaced. — [Red Canary 2026 TDR executive summary (Zscaler-hosted)](https://www.zscaler.com/resources/industry-reports/red-canary-2026-threat-detection-report-executive-summary.pdf); [BetaNews](https://betanews.com/article/cloud-accounts-come-under-attack-as-identity-threats-rise)
- Red Canary 2025: three of the top five techniques were cloud-native and identity-enabled; midyear update saw "Data from Cloud Storage" and "Disable or Modify Cloud Firewall" enter the top 10. — [Red Canary 2025 TDR](https://redcanary.com/blog/threat-detection/2025-threat-detection-report); [Midyear update](https://redcanary.com/blog/threat-detection/2025-threat-detection-report-midyear/)

- Enterprise average rule coverage is 21% of ATT&CK techniques despite large teams (CardinalOps 2025) — a ceiling-check on any "cover the matrix" ambition for a solo operator. — [Help Net Security](https://www.helpnetsecurity.com/2025/06/09/siem-detection-coverage/)

### Inferences
- **Priority technique list for one internet-facing personal VM [technique IDs from background knowledge; verify against attack.mitre.org]** — each should have (a) a deterministic check or rule, (b) a replay test:
  - Initial access: T1190 Exploit Public-Facing Application; T1133 External Remote Services; T1078 Valid Accounts; T1110 Brute Force.
  - Execution: T1059.004 Unix Shell (shell spawned by web/DB/app service user); T1203/T1068 exploitation for privilege escalation.
  - Persistence/priv-esc: T1098.004 SSH Authorized Keys; T1053.003 Cron; T1543.002 Systemd Service; T1546.004 shell config; T1136 Create Account; T1548.001 SUID/SGID, T1548.003 sudo; T1574.006 Dynamic Linker Hijacking; T1547.006 Kernel Modules; T1505.003 Web Shell; T1556.003 PAM.
  - Defence evasion: T1562.001 Impair Defenses (stop auditd/Falco, bpf map tampering), T1070 Indicator Removal (log wipe, history), T1222 permissions/attributes (`chattr +i`), T1014 Rootkit, T1036 Masquerading, T1620/T1055 in-memory execution.
  - Credential access: T1552.001 Credentials in Files (`.env`, cloud creds, SSH keys — honeytoken territory), T1003.008 `/etc/shadow`.
  - Discovery: low-value to alert on individually; useful as correlation context.
  - C2/exfil/impact: T1105 Ingress Tool Transfer (curl/wget to shell), T1071 application-layer C2, T1041/T1567 exfiltration, T1496 Resource Hijacking (miners), T1486 encryption.

- **Realistic coverage target:** ~30–40 techniques from the list above with *verified* (replayed) detections or preventive controls, tracked as technique → control/rule → test → last pass. That is a few percent of all techniques/sub-techniques in the Linux matrix but covers the bulk of what opportunistic actors actually do to a lone VM. Reporting "percent of matrix covered" is a vanity metric here; report "percent of priority list with a passing replay in the last 30 days".
- D3FEND is best used as a checklist for the *countermeasure* column (e.g. decoy objects, file integrity monitoring, outbound traffic filtering, credential hardening, system configuration permissions) so each priority technique has a harden/detect/deceive/evict entry **[background; D3FEND site not consulted this session]**.

## 9. Out-of-band integrity: getting evidence off the box

### Takeaway
On-box tamper-evidence (journald Forward Secure Sealing, immutable audit rules) only makes tampering *visible* and can itself be defeated by local root; the only robust control is to stream events off the host as they are written, into storage the VM's credentials cannot delete or rewrite (object-lock/WORM bucket or a tiny second VM), and to alert off-box when the stream stops.

### Cited Findings
- journald Forward Secure Sealing "does not prevent tampering; it makes it visible"; the sealing key is generated on the host and the verification key must be stored off-box; verification is on demand. — [StackHarbor KB: journald protection](https://stackharbor.com/en/knowledge-base/journald-protection/); [Netdata docs: FSS in systemd journal](https://learn.netdata.cloud/docs/logs-management/systemd-journal-logs/forward-secure-sealing-fss-in-systemd-journal)
- A local-root attacker can forge on-host verification results; authoritative tamper detection requires offline `journalctl --verify` against an exported archive using an off-host verification key (Ghaf architecture decision record). — [Ghaf ADR: Forward Secure Sealing for audit logs](https://ghaf.tii.ae/ghaf/overview/arch/adr/fss/)
- "The strongest guarantee is to ship every entry off the host as it is written"; `systemd-journal-upload` → `systemd-journal-remote` over HTTPS does this natively. — [StackHarbor KB](https://stackharbor.com/en/knowledge-base/journald-protection/)
- Academic analysis of journald's sealing scheme exists (KIT; IACR ePrint 2023/867) — findings not retrieved. — [ePrint 2023/867](https://eprint.iacr.org/2023/867.pdf)
- S3 Object Lock in compliance mode with a retention period prevents deletion even by the storage account's root user — usable as an append-only log sink. — [hoop.dev: immutable audit logs with AWS CLI](https://hoop.dev/blog/immutable-audit-logs-with-aws-cli-ensuring-truth-in-every-action); [OneUptime, Feb 2026: immutable audit log pipeline](https://oneuptime.com/blog/post/2026-02-06-immutable-audit-log-pipeline-otel/view)
- Root-level attackers do blind on-box sensors in practice and in PoCs (BPF map edits; `bpf` syscall hooking; LKM rootkits). — [dev.to bpftool post](https://dev.to/azqzazq1/i-silenced-falco-tracee-and-tetragon-with-a-single-bpftool-command-1i46); [Andrea Fortuna on eBPF rootkits / LinkPro](https://andreafortuna.org/2026/05/27/ebpf-rootkits/); [THC](https://iq.thc.org/breaking-ebpf-security-how-kernel-rootkits-blind-observability-tools)
- Honeypot attackers already use file attributes (`chattr`) to frustrate remediation — expect the same against local logs. — [SANS ISC diary 32024](https://isc.sans.edu/diary/32024)

### Inferences
- **Recommended shape:** VM runs a shipper (Vector/Fluent Bit or `systemd-journal-upload`) with a *write-only* credential → either (a) an object-storage bucket with Object Lock/retention and versioning, where the VM's key can `PutObject` only (no delete, no list, no lifecycle edit), or (b) a tiny second VM/home box that pulls or receives logs and that the first VM has no login to. The off-box side holds: raw alerts, the signed §3 inventory manifests, sensor health/heartbeats, and the FSS verification key.
- The LLM agent's analysis should preferably run against the off-box copy, with the on-box agent treated as an untrusted collector after any high-severity alert. The off-box side also runs the "stream stopped / heartbeat missing / manifest signature invalid" checks — the only detections a root attacker on the VM cannot suppress.
- Add *outside-in* probes from the second location: port scan vs expected listening set, TLS cert/SSH host-key fingerprint check, provider-API inventory (snapshots, firewall rules, attached keys). These see what a rootkit hides from userland.
- Shipping delay matters: batch uploads (e.g. every 5 minutes to object storage) leave a window in which an attacker can drop the unsent buffer; with key injection in ~22 s after login, prefer near-real-time streaming for auth and exec events, batch for the rest.
- Cost: this is the one place a few dollars/month (second smallest VM or object storage) buys a qualitatively different guarantee. Free hosted log tiers are an alternative but add a third party that sees your telemetry and impose retention limits **[background; no provider tiers verified]**.
