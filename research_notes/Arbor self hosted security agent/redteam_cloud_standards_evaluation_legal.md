## Key Question 1 — Safe automated attacks on your own production, and the legal/provider rules

### Takeaway
Testing your own instance and your own app is permitted without notice on the big three clouds and on Render/Fly, but every provider forbids DoS/volumetric tests and anything touching the provider's own infrastructure or other tenants; Oracle wants notification, and the small VPS providers (Hetzner, DigitalOcean, OVH, Linode, Vultr) have thin or unverified written policy plus automated abuse detection that can lock a server for outbound scanning. The real risks for a solo owner are not prosecution for attacking their own box but (1) the agent leaving scope (a documented 2026 failure mode for AI pentesters), (2) hitting an IP/hostname they no longer own, (3) third-party SaaS they do not own, and (4) damaging or leaking real users' personal data — so scope must be enforced outside the model, and authorization (BOLA/IDOR/logic) testing should rest on deterministic multi-user differential tests with LLM agents as a supplement.

### Inferences
- **Scope enforcement belongs in the network, not the prompt.** Given the AWS Security Agent case and that Strix/Shannon rely on warnings, the agent's attack sandbox should have a default-deny egress allow-list (resolved, pinned IPs of owned assets), a block on 169.254.169.254 and on provider control-plane API hosts from the attack sandbox, and a pre-run ownership check that asks the provider API "is this IP attached to my account right now?" plus a DNS TXT/HTTP challenge for each hostname. This also handles stale-DNS/IP-reuse collateral risk.
- **Launch-point matters on VPS providers.** Hetzner-style netscan detection keys on *outbound* scanning from the server. Running the scanner on the target VM against localhost/its own public IP, or from a home connection, avoids looking like an abusive scanner; scanning *from* the VPS toward anything else is the pattern that gets servers locked.
- **Running scans from GitHub-hosted Actions runners** is defensible when the target is the repo's own deployment (authorised access, "testing … of the software project"), but volume limits and "disproportionate burden" still apply and the traffic leaves from Microsoft-operated infrastructure; a self-hosted runner or the VM itself is the lower-risk choice for anything beyond a ZAP baseline or Nuclei detection pass.
- **Third-party SaaS is out of scope by construction.** Auth providers, payment APIs, CDNs and email/SMS providers are someone else's computer; the authorization concept in every statute above does not cover them. Practical pattern: in the staging clone, repoint their base URLs at stubs (provider sandbox/test mode where offered, an OpenAPI mock server, a local SMTP sink, a mock OIDC issuer) and add the real SaaS hostnames to the egress deny-list so a confused agent cannot reach them.
- **Safe-by-default class exclusions for prod**: no DoS/volumetric (every provider forbids it), no destructive SQL risk levels, no mass login attempts (lockouts), no stored payloads that render for real users, nothing that triggers real email/SMS/payment, and no exploit module whose metadata declares service crashes or config changes. Anything in those classes runs only against a snapshot clone on an isolated network.
- **The snapshot-clone is not automatically safe**: it contains production secrets and real personal data, and on boot may run cron jobs, send mail, or call production payment/webhook endpoints. It needs network isolation *before first boot*, secret rotation or stubbing, and ideally data scrubbing; fidelity gaps to accept are DNS/TLS, CDN/WAF behaviour, third-party callbacks and load.
- **GDPR/DPDP angle**: the owner testing their own system is not "unauthorised access", but a destructive payload, or prod personal data pasted into a third-party LLM API by the agent, plausibly is an accidental loss/disclosure. So the agent should redact response bodies before they reach the model, and prefer synthetic tenants and test accounts.
- **Documentation a solo owner should keep** (cheap, and it is what a provider abuse desk or a lawyer would ask for): (1) a dated, signed self-authorisation/scope file listing hostnames, IPs, cloud account IDs, excluded classes and time windows; (2) asset-ownership proof captured at test time (provider API output, registrar/DNS records); (3) an append-only test log with timestamp, source IP, tool, target and action, hash-chained; (4) a cleanup ledger of every artifact created (test users, uploaded files, webshells, tokens) with verification that each was removed; (5) a note of which provider policy version was read and when.
- **For authz/logic bugs, the evidence-backed order is**: owner-written abuse cases and ownership invariants → deterministic two-account differential replay on every endpoint → schema/stateful fuzzing in staging → white-box LLM review of handlers for missing ownership checks → black-box LLM agent as exploratory extra. LLM agents are the least proven layer for exactly the class the owner cares most about.

### Inferences
- **Concrete small-account stack (AWS example)**: Prowler CLI weekly with a `SecurityAudit`-based role → Access Analyzer external-access (free) always on, unused-access only if the per-principal fee is acceptable → Cloudsplaining on every policy change → Steampipe as the agent's ad-hoc query tool → 2–3 canary AWS keys planted on the VM and in the repo → Stratus Red Team in a *separate sandbox account* to prove GuardDuty/CloudTrail alerting works. GCP/Azure: same shape with SCC Standard + IAM Recommender, or Defender foundational CSPM.
- **For a Hetzner/DO-only owner, yes — the identity chain is the cloud attack surface.** There is no IAM graph to analyse; compromise paths run through (a) registrar account → DNS → issue TLS certs / reroute mail, (b) primary email → password resets for everything, (c) GitHub account/token → code and CI secrets → deploy to the VM, (d) provider console/API token → rebuild/snapshot the VM, (e) cloud-init user-data and metadata service leaking secrets to any local process. The agent's "cloud posture" module should therefore be a checklist over those accounts (hardware-key 2FA, registrar lock + DNSSEC, CAA records, token inventory with scope and expiry, deploy keys read-only, Actions pinned by SHA, provider firewall default-deny, off-provider backups, snapshot access) rather than a CSPM product. Prowler's GitHub and Cloudflare providers automate part of it.
- **Consuming scanners safely after TeamPCP**: pin GitHub Actions by full commit SHA and binaries by digest/checksum; apply a cool-down (don't adopt releases younger than several days); run scanners with a credential that can only read what they scan, no other secrets in the environment, and egress restricted to the vulnerability-DB hosts; prefer distro/pip installs with hash pinning over `curl | bash` installers (Strix's and Prowler's READMEs both show curl-pipe install paths).
- **Two-role pattern for the agent**: a permanently attached read-only audit role; a separate remediation role with a narrow, enumerated action list, a permissions boundary, a short session duration, assumable only after an out-of-band human approval (e.g. the approver's own credential is required in the trust policy), and an SCP that denies everything outside the owner's account IDs and regions. Use iamlive/Policy Sentry to derive the remediation policy from what the agent actually calls.
- PMapper's niche (privilege-escalation graphing) is now best covered by Prowler's Cartography-based Attack Paths for a self-hoster, though that needs the Prowler server stack and Neo4j — heavy for one account; Cloudsplaining + Access Analyzer is the light alternative.

## Key Question 3 — Standards worth encoding as machine-checkable policy

### Inferences
- **Encode first, in this order**: (1) CIS Level 1 for the distro via ComplianceAsCode/OpenSCAP (or ovh/debian-cis on Debian) with an explicit waiver file; (2) ssh-audit policy + TLS/headers baseline; (3) KSPP sysctl subset + `systemd-analyze security` threshold for the owner's services; (4) docker-bench / CIS Docker if containers are used; (5) cloud CIS via Prowler, or the VPS identity-chain checklist from Key Question 2; (6) CI: zizmor + Scorecard + SHA-pinning rule (directly motivated by TeamPCP); (7) ASVS Level 1 mapped item-by-item to a test, an agent review, or "manual"; (8) OWASP Agentic Top 10 as the agent's own control list.
- **Use as vocabulary, not policy**: ATT&CK (detections/scenarios), OWASP Top 10 / API Top 10 (finding labels), CIS Controls IG1 (index of the baseline), D3FEND (remediation verbs).
- **Explicitly skip as paperwork for a solo operator**: NIST CSF 2.0, SP 800-53, SSDF, PCI DSS (avoid scope instead), DISA STIG, S2C2F maturity scoring, CIS Level 2 wholesale, and CIS-CAT Pro/SecureSuite membership.
- **CIS licensing caution**: the benchmark *text* is under CIS terms; a self-hosted agent that might later be shared should reference the open re-implementations (ComplianceAsCode, ovh/debian-cis, dev-sec) and rule IDs rather than embed CIS prose.
- **Two engines are enough**: goss for "is the host in the state I declared" and OPA/conftest for "is this config/plan/agent action allowed"; OpenSCAP and Prowler are scanners whose output feeds those gates. Cedar is worth adding only for the agent's own permission model, where its analysability matters.
- docker-bench-security and kernel-hardening-checker have had no tagged release since 2023/2024; pin them and expect newer Docker/kernel options to be unchecked.

### Gaps
- OWASP's own Top 10:2025 pages, ASVS 5.0 requirement count, the Agentic Top 10 item list, CIS terms of use, and current ATT&CK version (v18 vs a 2026 v19) could not be fetched; items marked [K] are from memory.
- SLSA's current point version (1.1 vs 1.2 with a Source track) and whether SSDF v1.2 is final were not verified.
- Whether ComplianceAsCode ships a current CIS profile for the owner's exact distro release (e.g. Ubuntu 24.04 / Debian 13) was not checked; Canonical's USG/Ubuntu Pro route was not verified.
- InSpec/CINC and osquery release health were not checked.

## Key Question 4 — Evaluation: knowing the agent works

### Takeaway
Public benchmarks tell you whether the underlying model/harness is in the right league and nothing about your stack: offensive CTF-style sets are saturating or contaminated, while the two most relevant defensive benchmarks show how far agents still are (best model 72.4% on SecRespond with no range fully solved; ~56% average reward on ExCyTIn-Bench). The honest evaluation is a private, versioned suite of attack scenarios replayed against a clone of the owner's own VM after every agent change, scored on detection, cleanup completeness, fix correctness, regressions, cost and approvals, with a held-out subset and a separate hijack-resistance suite.

#### 4c. Defensive / IR benchmarks

- **SecRespond** — the claimed arXiv ID is real: arXiv 2607.26791, "SecRespond: Benchmarking AI Agents for Real-World Post-Compromise Incident Response", posted 29 July 2026 (Lehan Wang + nine co-authors; Alibaba). 10 cyber ranges on fully instantiated cloud hosts, 4 entry-point types, 21 ATT&CK techniques, 5 operating systems, 52 capability items, 280 checkpoints. Caveat: one harness, one version; the "none fully solved" claim awaits replication. ### Inferences
- **Why public scores will not predict performance on the owner's stack**: (1) saturation and contamination on CTF-style sets; (2) results are harness-specific (SecRespond's own caveat); (3) category blindness — business-logic/authorization, the owner's top risk, has three tasks in one study and no dedicated benchmark; (4) domain mismatch — CyberGym/SEC-bench/AIxCC are C/C++ fuzzing targets, ExCyTIn is Sentinel/Azure, most replay datasets are Windows; (5) none score *safety on production* (scope adherence, cleanup, regressions). Use them only as a go/no-go on the model + harness.
- **SecRespond is the closest public proxy for the product being built** (given a compromised Linux cloud host and its alerts, find everything and plan remediation), and its headline finding — alerted issues are found, silent ones and complete remediation are not — is the failure mode to design the private suite around.
- **Private regression suite design**: on a snapshot-clone of the real VM, define 20–40 scenarios as code, each with (a) an injector (Atomic Red Team Linux atomic, PANIX persistence, a Vulhub service, a seeded IDOR in a synthetic tenant, a planted leaked canary key, a Stratus technique in the sandbox account), (b) ground truth (artifacts created, ATT&CK ID, expected alert), (c) an oracle (artifact absent after cleanup; exploit PoC fails after patch; app health checks still pass). Keep ~25% as held-out canary scenarios the developer never tunes against, rotate them, and add 10–20% benign "look-alike" scenarios (legit cron job, admin SSH from a new IP, a deploy) to measure false positives. Re-run the whole suite on every prompt/model/tool change.
- **Metric definitions that work on one VM**:

| Metric | How to measure on a personal setup |
|---|---|
| MTTD / MTTR | Injector timestamp → first correct alert → oracle confirms clean; report median and worst case per scenario class. |
| Detection coverage | Table of technique × data source × rule × last-validated date (DeTT&CT/VECTR style); a rule not exercised by a scenario in N days is "unvalidated", not "covered". |
| Alert precision / FP rate | Run a benign week on the real VM with no injections: alerts per day and fraction actionable; plus precision on the look-alike scenarios. |
| Persistence-removal completeness | PANIX/atomics create k artifacts; score removed/k and require 100% for a pass (SecRespond's result says partial credit hides the real failure). |
| Fix success rate | Patch applied and the original exploit PoC now fails. |
| Still-exploitable-after-patch rate | Re-attack with variants (different parameter, second account, different encoding) after the fix. |
| Regression rate (fixes that broke something) | App smoke tests + goss baseline + service health after each fix; count failures per fix. |
| Cost per finding / per validated finding | LLM + compute spend divided by findings that survive PoC validation; track unvalidated findings separately as noise. |
| Approval load | Human approvals requested per week and median time-to-approve; set an explicit budget (approval fatigue is a safety failure, not a UX nit). |
| Agent safety | Out-of-scope connection attempts blocked by the egress layer; policy-engine denials by rule; prompt-injection attack success rate on an AgentDojo-style suite adapted to the agent's real tools (injections planted in log lines, HTTP responses, file names, repo READMEs). |
| Drift | Diff of goss/OpenSCAP/Lynis/Prowler results against the signed baseline per day. |

- **Budget order for a solo owner**: local containers first (Vulhub, crAPI/VAmPI, Juice Shop, PANIX and atomics on a clone — effectively free), then one throwaway cloud sandbox account for Stratus/CloudGoat (destroy after each run), and only then paid model spend for a small public-benchmark sanity run through `inspect_evals`. Splunk Attack Range, Ludus and GOAD are more range than a one-VM Linux owner needs.
- **Hijack resistance needs its own suite** because a security agent reads attacker-controlled text by design (logs, web responses, malware strings); generic AgentDojo scores are a starting point, but the meaningful number is attack success rate with injections placed in the agent's actual input channels, measured with the egress allow-list both on and off to separate model robustness from containment.

### Gaps
- Could not re-verify headline numbers for Cybench, NYU CTF Bench, InterCode-CTF, AutoPenBench, CyberGym, SEC-bench, BountyBench, CyberSecEval 4/AutoPatchBench, CyberSOCEval, AIxCC, CTIBench, IRCopilot or DFIR-Metric (arxiv.org unreachable, search budget exhausted); their rows carry [K] and deliberately omit precise figures where I was not confident.
- XBOW-benchmark scores claimed by Shannon, Strix, CAI and XBOW were not retrieved; no independent head-to-head of the open-source agents on the same harness was found.
- Licences for most benchmarks/datasets were not individually confirmed (verified: inspect-evals MIT, Prowler/Strix Apache-2.0, Shannon AGPL-3.0, CAI dual MIT/proprietary).
- Cost to run each benchmark (model spend per full pass) was not found in any retrieved source.
- Hack The Box / TryHackMe "AI range" offerings and MCP-specific academic suites (MCPTox, MCP-SafetyBench, MCPSecBench) were not verified.
- No Linux-host-focused public replay dataset newer than BETH (2021) was identified; this is a reason to generate one's own telemetry from the private scenario suite.
- I found no published benchmark that scores an agent on production-safety properties (scope adherence, cleanup completeness, regression rate); those metrics above are my proposal, not an established standard.
